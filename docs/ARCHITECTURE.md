# Архитектура

## Общая картина

```
 ┌──────────────── Pepa.exe (Windows) ────────────────┐      ┌──── pepa-server (без окна) ────┐
 │  WPF-окно  ── WebView2 ──┐                          │      │  тот же Pepa.Host               │
 │  (выбор папки, проводник, │ http://127.0.0.1:порт   │      │  интерфейс — в обычном браузере │
 │   закрытие, активация)    ▼                          │      └─────────────────────────────────┘
 │  Pepa.Host: Kestrel ─ /api (JSON) + /api/stream (SSE) + интерфейс (wwwroot)                 │
 │        │                                                                                    │
 │  Pepa.Engine: процессы, маркеры, шаги, таймер, восстановление ── Pepa.Storage.Sqlite (WAL)  │
 │        │                                                                                    │
 │  Pepa.Core: модель сценария, описания блоков, проверка, выражения (Jint)                    │
 │        │                                                                                    │
 │  Адаптеры: FileSystem, Browser (Playwright + AdsPower), Telegram, Desktop (UI Automation) │
 └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

Движок работает в том же процессе, что и окно. Интерфейс — веб-приложение, которое получает данные только
через локальный API. Тот же API используется сервером без окна (разработка, автотесты, в будущем — работа на
Windows-сервере без включённого ПК пользователя).

## Сущности исполнения

- **Сценарий** (`ScenarioDefinition`) — граф: блоки (`nodes`), связи (`edges`) из именованного выхода блока во вход
  другого, объявленные переменные. Хранится с номером версии.
- **Процесс** (`ProcessRecord`) — запуск сценария. Хранит **снимок** сценария на момент запуска, свои переменные,
  состояние и объяснение состояния.
- **Маркер** (`TokenRecord`) — где сейчас процесс: блок, готов/ждёт/завершён, срок пробуждения, номер попытки.
  У процесса с параллельными ветвями маркеров несколько: «Параллельно» создаёт по маркеру на ветвь и записывает в
  них участок (`fork`: «id:число ветвей», вложенные — через «/»); «Дождаться всех ветвей» держит пришедшие маркеры
  (`WaitKind.Join`), пока не придут все, и продолжает одним. Шаги ветвей выполняются по очереди одним исполнителем
  процесса — одновременно идут ожидания. Решение пользователя относится к ветви, которая остановилась
  (`processes.attention_token_id`).
- **Шаг** (`StepRecord`) — одно выполнение блока: вычисленные параметры, снимок «до», результат, ошибка, решение.
- **Журнал** (`JournalEntry`) — понятные сообщения о важных событиях процесса.
- **Событие** (`EventRecord`) — входящее сообщение: источник, вид, ключ сопоставления, данные, ключ от повторов
  (уникален вместе с источником), состояние обработки.
- **Подписка** (`SubscriptionRecord`) — чего ждёт шаг процесса: источник, вид, ключ, условие, приоритет, окно,
  срок. Состояния: ждёт → получено | тайм-аут | отменено. Смена состояния — атомарная («только если сейчас ждёт»).
- **Ресурс** (`ResourceRecord`) и **очередь** (`ResourceWaiterRecord`) — кто держит ресурс и кто ждёт его по порядку.
- **Триггер** (`TriggerRecord`) — запуск сценария по расписанию или событию, со счётчиками пропущенных запусков.
- **Память блока** (`processes.memory`) — состояние блока между его выполнениями (позиция цикла).

### Состояния процесса

`running → waiting → running → … → completed | failed | cancelled`; в любой момент — `paused` (пользователь или
перезапуск) и `needsAttention` (нужно решение). Из `paused` и `needsAttention` процесс выходит **только по действию
пользователя**. Какие действия доступны, решает движок (`GetAllowedActions`); интерфейс показывает только их.

### Состояния шага

| Состояние | Значение |
|---|---|
| `planned` | создан, не начат |
| `running` | записано на диск **до** вызова внешнего действия |
| `waiting` | ждёт срока, события, ресурса или завершения вызванного сценария |
| `succeeded` | подтверждён выполненным |
| `failed` | подтверждён не выполненным (повтор безопасен) |
| `unknown` | неизвестно, выполнилось ли действие (повтор вслепую запрещён) |
| `skipped`, `cancelled` | пропущен пользователем / отменён |

## Как выполняется шаг

1. Параметры блока вычисляются (шаблоны `{{ … }}`, выражения) и сохраняются в шаге.
2. Блок без внешних эффектов (`effect: none`) выполняется и фиксируется одной транзакцией.
3. Действие с эффектом: `planned` → `Prepare` (снимок состояния «до», только чтение) → запись `running` →
   `Execute` с тайм-аутом → при исключении/тайм-ауте итог `unknown` → сразу `Verify` (проверка, не повтор):
   «выполнено» → `succeeded`, «не выполнено» → `failed`, «неясно» → `unknown` → процесс `needsAttention`.
4. Итог применяется одной транзакцией: шаг, переменные, переход маркера, состояние процесса, журнал.
5. Подтверждённая ошибка: повтор по настройкам блока → ветка «Ошибка» (если подключена) → иначе `needsAttention`.
   Для `unknown` повторы не применяются никогда.

Действия «только чтение» (`effect: readOnly`) не могут получить итог `unknown`: их сбой — обычная ошибка.

### Действия платформы

Блоки событий, ресурсов и вызова сценариев ничего не делают во внешнем мире — они возвращают движку намерение
(`WaitForEvent`, `AcquireResource`, `ReleaseResource`, `PublishEvent`, `StartChild`). Движок применяет его в той же
транзакции, что и итог шага: подписка, место в очереди, занятие ресурса, новое событие или дочерний процесс
появляются вместе с шагом или не появляются вовсе. Последствия, которые сами пишут в хранилище (вернуть события на
сопоставление, остановить дочерний процесс), выполняются после закрытия транзакции.

Если процесс должен пойти по необязательному выходу (например, «Тайм-аут»), а он не подключён, шаг считается
невыполненным: дальше — ветка «Ошибка» или решение пользователя.

### Сопоставление событий

Фоновый маршрутизатор берёт принятые события по порядку и для каждого ищет действующие подписки: тот же источник,
вид (если задан), ключ (если задан), событие пришло во время ожидания или в разрешённое окно до него, условие
(если задано) даёт `true`. Один кандидат с наибольшим приоритетом — событие назначается ему; несколько равных —
конфликт; ни одного — триггеры по событию, иначе «никому не подошло». Новая подписка с окном «пришедшие раньше»
возвращает на сопоставление подходящие по времени необработанные события.

Источники событий: API (`http`, `manual`), процессы (`process`, служебный `pepa.process`), Telegram (`telegram`) и
слежение за папками (`files`, `FolderWatcher`, D-051). События, которые произошли у источника до запуска Pepa
(`OccurredAt` раньше запуска движка), отдаются ожидающим процессам, но триггеры по ним процессы не запускают.

### Ресурсы

Свободный ресурс занимается сразу (если в очереди нет активных ожидающих). Занятый — процесс встаёт в очередь
и ждёт, не занимая исполнителя. При освобождении (блоком, завершением процесса или вручную) ресурс сразу получает
первый ожидающий процесс в состоянии «ожидает». Перед постановкой в очередь проверяется цепочка «кто кого ждёт»:
цикл — взаимная блокировка, запросивший процесс останавливается с объяснением.

## Восстановление

При старте движок, ничего не выполняя:
- шаги `running` → `unknown` («приложение закрылось во время шага»), процесс → `needsAttention`;
- шаги `planned` → `cancelled` (они не начинались; при возобновлении будут запланированы заново);
- процессы `running`/`waiting` → `paused` (причина — перезапуск);
- ресурсы, которые числятся за завершёнными процессами, освобождаются; очередь чистится от них же;
- расписания, чей срок прошёл, пока приложение было закрыто, получают счётчик пропущенных запусков и следующий
  срок — сами пропущенные запуски не выполняются;
- принятые до закрытия события сопоставляются, но применяются процессами только после ручного возобновления;
- если база — восстановленная резервная копия (в ней отметка `pepa_backup`), каждый незавершённый процесс → `needsAttention`
  («база восстановлена из копии»: что он сделал после копии, неизвестно), затем отметка снимается (D-047).

Таймер будит только процессы в состоянии `waiting`, поэтому приостановленные не продолжатся сами. Сбой
хранилища во время работы приводит процесс к тому же согласованному состоянию (или, если записать не удалось,
это сделает восстановление при следующем запуске).

## Параллельность

- Шаги одного процесса — строго последовательно: правом изменять процесс владеет либо исполнитель, либо
  управляющая операция (`ProcessSlot`). Пауза и остановка во время шага откладываются до границы шага;
  остановка дополнительно отменяет токен отмены действия.
- Разные процессы — параллельно, не больше `MaxParallelProcesses`. Ожидающие процессы исполнителя не занимают.
- Процесс, сделавший много шагов подряд, уступает исполнителя другим (`StepsPerSlice`).
- Лимит шагов (`StepBudget`) останавливает бесконечные циклы с вопросом пользователю.

## Хранилище

Один файл `pepa.db` в папке данных (`%LOCALAPPDATA%\Pepa`). Таблицы `scenarios`, `processes`, `tokens`, `steps`,
`journal`, `settings`, `events`, `subscriptions`, `resources`, `resource_waiters`, `triggers`. WAL, `synchronous=FULL`, внешние ключи, все записи — через один замок. Схема
версионируется `PRAGMA user_version`; база более новой версии не открывается старым приложением. Секретные значения
процесса и события (`processes.secrets`, `events.secrets`, D-055) хранятся настоящими, как переменные, и скрываются
только при показе.

Обслуживание (в фоне, в `Pepa.Host`):
- `DatabaseBackups` — копии базы в `backups/`: раз в сутки, по кнопке, перед обновлением схемы. В каждой копии —
  отметка `pepa_backup`, по которой восстановленная база узнаётся при запуске (D-047).
- `HistoryRetention` — удаление старых завершённых процессов и данных старых событий по сроку из «Настроек» (D-049, D-071).
- `SnapshotFolder` — снимки экрана при ошибках шагов в папке данных (`snapshots/<процесс>/`), не больше 20 на процесс (D-072).
- `AttentionNotifier` — уведомления о процессах, ждущих решения: окно (`IDesktopAlerts`) и «Избранное» Telegram (D-048).
- `FolderWatcher` (в `Pepa.Adapters.FileSystem`) — проверка отслеживаемых папок раз в 2 секунды; списки известных файлов —
  в `watches/<номер>.json` папки данных (D-051).

## Локальный API и безопасность

- Kestrel слушает только `127.0.0.1` на случайном порту.
- Для `/api` обязателен заголовок `X-Pepa-Token` (случайный при каждом запуске; окно передаёт его во фрагменте
  адреса `#token=…`, который не уходит на сервер). Заголовок `Host` должен быть `127.0.0.1`/`localhost` с нашим
  портом — защита от DNS rebinding.
- Изменения отправляются интерфейсу потоком SSE (`/api/stream`) со склейкой частых событий.
- Нативные функции окна (выбор папки, открыть папку) — через `chrome.webview.postMessage`, только для страницы
  самого Pepa; «открыть папку» принимает только существующие папки.

Основные адреса: `GET /api/info`, `GET /api/node-types`, `GET|POST /api/scenarios`, `GET|PUT|DELETE /api/scenarios/{id}`,
`POST /api/scenarios/{id}/duplicate|run`, `POST /api/scenarios/validate`, `GET /api/processes?view=active|finished|attention|all`,
`GET /api/processes/{id}`, `POST /api/processes/{id}/pause|cancel|resume`, `GET /api/overview`, `GET|PUT /api/settings`,
`GET|POST /api/events`, `POST /api/events/{id}/resolve|reroute`, `GET /api/resources`, `POST /api/resources/release`,
`GET|POST /api/triggers`, `PUT|DELETE /api/triggers/{id}`, `POST /api/triggers/{id}/run|dismiss`, `GET /api/stream`.

`POST /api/events` — способ передать событие из своей программы на этом компьютере (с тем же токеном).

## Браузер и AdsPower

`BrowserSessions` хранит открытые браузеры процессов (один экземпляр Playwright на приложение, у процесса — сессии
по имени, обычно `main`). Список сессий записывается в `browser-sessions.json` в папке данных: после перезапуска
Pepa к ещё открытому профилю AdsPower можно подключиться снова. `AdsPowerClient` — Local API (v2, запасной v1,
ключ `Authorization: Bearer`, запросы по одному с паузой). Блоки «Открыть браузер» и «Открыть профиль AdsPower»
объявляют нужный ресурс (`INodeExecutor.RequiredResource`): движок занимает его до действия — сразу или в очереди —
и выполняет блок снова, уже с ресурсом. Ресурс освобождается блоком «Закрыть браузер» (`Success.ReleaseResources`)
или при завершении процесса; по событию `ProcessFinished` модуль закрывает браузеры процесса.

## Как добавить новый блок

1. Реализовать `INodeExecutor` с описанием `NodeTypeDescriptor`: тип, категория, поля (вид поля определяет редактор
   в конструкторе и способ вычисления значения), выходы, `effect`. Если блоку нужен монопольный ресурс —
   `RequiredResource`; если действие может длиться дольше общего тайм-аута — `ExpectedDuration`.
2. Для внешних действий — `PrepareAsync` (снимок «до») и `VerifyAsync` (проверка без повтора), если это возможно.
   Ошибки параметров — `NodeInputException` (действие заведомо не выполнялось).
3. Зарегистрировать в `NodeRegistry` (для адаптера — метод-расширение `Register…Nodes`).
4. Тесты поведения и проверки результата.

Интерфейс подхватывает новый блок автоматически: палитра, форма свойств и проверка строятся по описанию.
