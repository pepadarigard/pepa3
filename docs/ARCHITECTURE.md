# Архитектура

## Общая картина

```
 ┌──────────────── Pepa.exe (Windows) ────────────────┐      ┌──── pepa-server (без окна) ────┐
 │  WPF-окно  ── WebView2 ──┐                          │      │  тот же Pepa.Host               │
 │  (выбор папки, проводник, │ http://127.0.0.1:порт   │      │  интерфейс — в обычном браузере │
 │   закрытие, активация)    ▼                          │      └─────────────────────────────────┘
 │  Pepa.Host: Kestrel ─ /api (JSON) + /api/events (SSE) + интерфейс (wwwroot)                 │
 │        │                                                                                    │
 │  Pepa.Engine: процессы, маркеры, шаги, таймер, восстановление ── Pepa.Storage.Sqlite (WAL)  │
 │        │                                                                                    │
 │  Pepa.Core: модель сценария, описания блоков, проверка, выражения (Jint)                    │
 │        │                                                                                    │
 │  Адаптеры: Pepa.Adapters.FileSystem (дальше: браузер, UI Automation, AdsPower, Telegram)    │
 └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

Движок работает в том же процессе, что и окно. Интерфейс — веб-приложение, которое получает данные только
через локальный API. Тот же API используется сервером без окна (разработка, автотесты, в будущем — работа на
Windows-сервере без включённого ПК пользователя).

## Сущности исполнения

- **Сценарий** (`ScenarioDefinition`) — граф: блоки (`nodes`), связи (`edges`) из именованного выхода блока во вход
  другого, объявленные переменные. Хранится с номером версии.
- **Процесс** (`ProcessRecord`) — запуск сценария. Хранит **снимок** сценария на момент запуска, свои переменные,
  состояние и объяснение состояния.
- **Маркер** (`TokenRecord`) — где сейчас процесс: блок, готов/ждёт/завершён, срок пробуждения, номер попытки.
  Сейчас у процесса один маркер; параллельные ветви добавят несколько.
- **Шаг** (`StepRecord`) — одно выполнение блока: вычисленные параметры, снимок «до», результат, ошибка, решение.
- **Журнал** (`JournalEntry`) — понятные сообщения о важных событиях процесса.

### Состояния процесса

`running → waiting → running → … → completed | failed | cancelled`; в любой момент — `paused` (пользователь или
перезапуск) и `needsAttention` (нужно решение). Из `paused` и `needsAttention` процесс выходит **только по действию
пользователя**. Какие действия доступны, решает движок (`GetAllowedActions`); интерфейс показывает только их.

### Состояния шага

| Состояние | Значение |
|---|---|
| `planned` | создан, не начат |
| `running` | записано на диск **до** вызова внешнего действия |
| `waiting` | блок «Ожидание» ждёт срока |
| `succeeded` | подтверждён выполненным |
| `failed` | подтверждён не выполненным (повтор безопасен) |
| `unknown` | неизвестно, выполнилось ли действие (повтор вслепую запрещён) |
| `skipped`, `cancelled` | пропущен пользователем / отменён |

## Как выполняется шаг

1. Параметры блока вычисляются (шаблоны `{{ … }}`, выражения) и сохраняются в шаге.
2. Блок без внешних эффектов (`effect: none`) выполняется и фиксируется одной транзакцией.
3. Действие с эффектом: `planned` → `Prepare` (снимок состояния «до», только чтение) → запись `running` →
   `Execute` с тайм-аутом → при исключении/тайм-ауте итог `unknown` → сразу `Verify` (проверка, не повтор):
   «выполнено» → `succeeded`, «не выполнено» → `failed`, «неясно» → `unknown` → процесс `needsAttention`.
4. Итог применяется одной транзакцией: шаг, переменные, переход маркера, состояние процесса, журнал.
5. Подтверждённая ошибка: повтор по настройкам блока → ветка «Ошибка» (если подключена) → иначе `needsAttention`.
   Для `unknown` повторы не применяются никогда.

Действия «только чтение» (`effect: readOnly`) не могут получить итог `unknown`: их сбой — обычная ошибка.

## Восстановление

При старте движок, ничего не выполняя:
- шаги `running` → `unknown` («приложение закрылось во время шага»), процесс → `needsAttention`;
- шаги `planned` → `cancelled` (они не начинались; при возобновлении будут запланированы заново);
- процессы `running`/`waiting` → `paused` (причина — перезапуск).

Таймер будит только процессы в состоянии `waiting`, поэтому приостановленные не продолжатся сами. Сбой
хранилища во время работы приводит процесс к тому же согласованному состоянию (или, если записать не удалось,
это сделает восстановление при следующем запуске).

## Параллельность

- Шаги одного процесса — строго последовательно: правом изменять процесс владеет либо исполнитель, либо
  управляющая операция (`ProcessSlot`). Пауза и остановка во время шага откладываются до границы шага;
  остановка дополнительно отменяет токен отмены действия.
- Разные процессы — параллельно, не больше `MaxParallelProcesses`. Ожидающие процессы исполнителя не занимают.
- Процесс, сделавший много шагов подряд, уступает исполнителя другим (`StepsPerSlice`).
- Лимит шагов (`StepBudget`) останавливает бесконечные циклы с вопросом пользователю.

## Хранилище

Один файл `pepa.db` в папке данных (`%LOCALAPPDATA%\Pepa`). Таблицы `scenarios`, `processes`, `tokens`, `steps`,
`journal`, `settings`. WAL, `synchronous=FULL`, внешние ключи, все записи — через один замок. Схема
версионируется `PRAGMA user_version`; база более новой версии не открывается старым приложением.

## Локальный API и безопасность

- Kestrel слушает только `127.0.0.1` на случайном порту.
- Для `/api` обязателен заголовок `X-Pepa-Token` (случайный при каждом запуске; окно передаёт его во фрагменте
  адреса `#token=…`, который не уходит на сервер). Заголовок `Host` должен быть `127.0.0.1`/`localhost` с нашим
  портом — защита от DNS rebinding.
- Изменения отправляются интерфейсу потоком SSE (`/api/events`) со склейкой частых событий.
- Нативные функции окна (выбор папки, открыть папку) — через `chrome.webview.postMessage`, только для страницы
  самого Pepa; «открыть папку» принимает только существующие папки.

Основные адреса: `GET /api/info`, `GET /api/node-types`, `GET|POST /api/scenarios`, `GET|PUT|DELETE /api/scenarios/{id}`,
`POST /api/scenarios/{id}/duplicate|run`, `POST /api/scenarios/validate`, `GET /api/processes?view=active|finished|attention|all`,
`GET /api/processes/{id}`, `POST /api/processes/{id}/pause|cancel|resume`, `GET /api/overview`, `GET|PUT /api/settings`,
`GET /api/events`.

## Как добавить новый блок

1. Реализовать `INodeExecutor` с описанием `NodeTypeDescriptor`: тип, категория, поля (вид поля определяет редактор
   в конструкторе и способ вычисления значения), выходы, `effect`.
2. Для внешних действий — `PrepareAsync` (снимок «до») и `VerifyAsync` (проверка без повтора), если это возможно.
   Ошибки параметров — `NodeInputException` (действие заведомо не выполнялось).
3. Зарегистрировать в `NodeRegistry` (для адаптера — метод-расширение `Register…Nodes`).
4. Тесты поведения и проверки результата.

Интерфейс подхватывает новый блок автоматически: палитра, форма свойств и проверка строятся по описанию.
