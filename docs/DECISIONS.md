# Архитектурные решения

Формат: решение → почему → последствия. Новые решения добавляются в конец; отменённые не удаляются, а помечаются.

## D-001. C# и .NET 10 (LTS)
- **Почему:** нативный доступ к Windows (UI Automation, SendInput, WebView2), зрелая экосистема, долгая поддержка.
- **Последствия:** все проекты, кроме оболочки, — `net10.0` (собираются и тестируются на любой ОС);
  оболочка — `net10.0-windows`.

## D-002. Модульный монолит из небольшого числа проектов
- **Почему:** 13 модулей из ТЗ — это границы ответственности, а не обязательно отдельные сборки. Лишние проекты
  дают церемонии без пользы.
- **Последствия:** проекты `Core`, `Engine`, `Storage.Sqlite`, `Adapters.*`, `Host`, `Server`, `Desktop`.
  Направление зависимостей строго одно: `Core ← Engine ← (Storage, Adapters) ← Host ← (Server, Desktop)`.
  Модуль выносится в отдельный проект, когда появляется реальная причина (своя зависимость, своя платформа).

## D-003. Интерфейс целиком на React внутри WebView2, WPF — тонкая оболочка
- **Почему:** один UI-стек вместо двух; конструктор и история показывают одну и ту же схему; веб-интерфейс
  можно проверять автоматически (Playwright) на любой ОС, в том числе там, где ведётся разработка.
- **Последствия:** WPF отвечает за окно, жизненный цикл, нативные функции (выбор папки, открыть в проводнике,
  в будущем — трей, горячие клавиши, оверлеи записи и выбора элементов). WebView2 Runtime есть в Windows 10/11.

## D-004. Мост «интерфейс ↔ движок» — локальный HTTP API, а не postMessage
- **Почему:** один и тот же API работает в WebView2, в обычном браузере (разработка, тесты) и в будущем —
  для удалённого просмотра. Нет двух реализаций моста.
- **Безопасность:** Kestrel слушает только `127.0.0.1`, случайный порт; каждый запрос к `/api` требует
  случайный токен в заголовке `X-Pepa-Token`; проверяется заголовок `Host` (защита от DNS rebinding).
  Сторонний сайт в браузере не может прочитать токен и не может вызвать API.
- **Последствия:** нативные функции, которых нет в браузере, идут через `chrome.webview.postMessage`
  и в обычном браузере просто скрыты.

## D-005. Сценарий — граф узлов и связей; исполнение через «маркеры»
- **Почему:** граф естественно описывает ветвления, циклы (обратные связи), ожидания и в будущем — параллельные
  ветви; состояние процесса = где стоят маркеры + переменные; это легко сохранять и восстанавливать.
  React Flow рисует такой граф напрямую. Запись действий даёт линейную цепочку в том же формате.
- **Последствия:** у каждого выходного порта ровно одна связь (никакого неявного параллелизма). Параллельность
  появится только через явные узлы «разделение/слияние» со структурной проверкой. Формат версионируется
  (`schemaVersion`).

## D-006. Надёжность исполнения — в ядре с первого этапа (изменение порядка этапов ТЗ)
- **Почему:** если сделать движок «в памяти», на этапе 2 его пришлось бы переписывать.
- **Последствия:** уже в первой версии каждый шаг проходит состояния «запланирован → выполняется →
  подтверждён / не выполнен / неизвестно / ожидает», а переход в «выполняется» записывается на диск до вызова
  внешнего действия. Ожидание — запись в базе, а не спящий поток.

## D-007. Снимок состояния + журнал, а не полноценный event sourcing
- **Почему:** сценарий — интерпретируемые данные, а не пользовательский код, поэтому нет нужды «переигрывать»
  историю, как в Temporal. Снимок проще, журнал даёт историю и диагностику.
- **Последствия:** таблицы `processes`, `tokens`, `steps`, `logs`; каждый переход — одна транзакция.

## D-008. SQLite через Microsoft.Data.Sqlite, без ORM
- **Почему:** полный контроль над транзакциями и схемой, мало зависимостей.
- **Последствия:** WAL, `synchronous=FULL` (запись о начале внешнего действия не теряется при сбое питания),
  все записи сериализованы одним замком; миграции по `PRAGMA user_version`. Скорость при этом достаточна:
  десятки и сотни шагов в секунду.

## D-009. Выражения — JavaScript (Jint) в песочнице
- **Почему:** синтаксис знаком пользователям и ИИ; есть строки, регулярные выражения, даты, JSON. Свой язык
  дольше и всё равно упёрся бы в эти потребности.
- **Последствия:** лимиты времени, памяти, рекурсии и числа операций; нет доступа к .NET, файлам и сети.
  Условие обязано вернуть `true/false` (строгая проверка вместо «правдоподобных» значений).
  Шаблоны строк: `Привет, {{ vars.name }}`.

## D-010. Восстановление консервативно; результат внешних действий сверяется, а не повторяется
- **Почему:** требование ТЗ — не повторять действие с неизвестным результатом.
- **Последствия:** у действия есть необязательные `Prepare` (снимок «до») и `Verify` (проверка «выполнилось ли»).
  После перезапуска процессы приостановлены; шаг, прерванный посреди выполнения, получает статус «неизвестно».
  При ручном возобновлении сначала выполняется проверка; если она невозможна или неоднозначна — решает пользователь.

## D-011. Базовый визуальный конструктор — уже на первом этапе (изменение порядка этапов ТЗ)
- **Почему:** интерфейс веб-ориентированный (D-003), конструктор на React Flow не требует отдельной
  инфраструктуры, а без него пользователь не может удобно создавать и проверять сценарии.
- **Последствия:** этап 3 становится «развитием конструктора» (подпроцессы, параллельные ветви, отладка по шагам и т.д.).

## D-012. Разработка в облачном Linux-контейнере, проверка Windows — через GitHub Actions
- **Почему:** так работа не зависит от того, включён ли ПК пользователя.
- **Последствия:** всё, кроме оболочки, собирается и тестируется в контейнере; оболочка компилируется там же
  (`EnableWindowsTargeting`). Сборка и тесты на Windows и готовый архив приложения — в GitHub Actions.

## D-013. Один экземпляр на папку данных
- **Почему:** два экземпляра над одной базой исполнили бы одни и те же шаги дважды.
- **Последствия:** эксклюзивная блокировка файла `instance.lock` в папке данных на всё время работы.

## D-014. Файловые действия ограничены рабочей папкой
- **Почему:** первое действие должно быть безопасным; ошибка в пути не должна задеть чужие файлы.
- **Последствия:** любые пути разрешаются относительно рабочей папки; выход за её пределы (`..`, абсолютные пути,
  ссылки/junction) запрещён. Это основа будущей системы разрешений.

## D-015. Интерфейс на русском, строки отдельно от кода
- **Последствия:** тексты интерфейса — в `ui/src/i18n`; сообщения движка и проверки — с кодом и русским текстом.

## D-016. Событие применяет сам процесс, а не маршрутизатор
- **Почему:** состояние процесса меняет только его владелец (`ProcessSlot`). Маршрутизатор лишь назначает событие
  подписке (атомарная смена «ждёт → получено» в хранилище), а процесс применяет его своим обычным шагом.
- **Последствия:** событие для приостановленного или требующего решения процесса остаётся «назначенным» и
  применяется только после возобновления. Если процесс завершился, не применив событие, оно возвращается на
  сопоставление. Сопоставление идёт по одному событию за раз (замок маршрутизатора), в порядке поступления.

## D-017. Неоднозначность — не угадываем
- **Почему:** ТЗ требует не выполнять незапланированных действий.
- **Последствия:** если событие одинаково подходит нескольким процессам (одинаковый наивысший приоритет), оно
  получает состояние «нужно решение» и не отдаётся никому; пользователь выбирает получателя или пропускает событие.
  Событие, которое никто не ждёт и не запускает триггер, сохраняется как «никому не подошло». Процессы,
  начавшие ждать позже, могут забрать его, только если явно разрешили окно «пришедшие раньше».
  Ключ сопоставления, который задан, но получился пустым (не заполнена переменная), — ошибка шага, а не «любой ключ».

## D-018. Ресурсы: очередь по порядку, приостановленные пропускаются, но сохраняют место
- **Почему:** ожидание не должно блокировать других (ТЗ), а приостановленный процесс не может воспользоваться
  ресурсом. Отдавать ресурс процессу на паузе — значит держать его впустую.
- **Последствия:** при освобождении ресурс получает первый в очереди процесс в состоянии «ожидает». Ресурсы
  приостановленного процесса остаются за ним (он мог оставить профиль открытым) — освободить можно вручную.
  Взаимная блокировка (процесс ждёт ресурс у того, кто ждёт его ресурс) обнаруживается при запросе и
  останавливает запросивший процесс с объяснением. После сбоя ресурсы завершённых процессов освобождаются.

## D-019. Расписания без cron; пропущенное не запускается само
- **Почему:** понятность для пользователя важнее выразительности; ТЗ запрещает автозапуск после перезапуска.
- **Последствия:** три вида расписания: каждые N минут (от местной полуночи), по дням недели, один раз. Каждый
  запуск имеет ключ происхождения (`schedule:{триггер}:{время}`, `event:{триггер}:{событие}`), уникальный в базе, —
  двойной запуск невозможен. Пока Pepa была закрыта, запуски считаются пропущенными и показываются на главной.
  «Не запускать, пока работает предыдущий» включено по умолчанию. Событие, которое ждёт работающий процесс,
  достаётся ему, а не триггеру. Запуск, опоздавший больше чем на 10 минут при открытом приложении (например,
  компьютер спал), тоже считается пропущенным. Интервал, укладывающийся в сутки, отсчитывается от местной
  полуночи, остальные — ровной сеткой без сбоя в полночь.

## D-020. Вызов сценария: дочерний процесс, итог — событием
- **Почему:** дочерний процесс — полноценный процесс со своим состоянием, журналом и восстановлением; ожидание
  его итога — то же ожидание события (без отдельного механизма).
- **Последствия:** «Вызвать сценарий» создаёт дочерний процесс в той же транзакции, что и шаг, и ждёт служебное
  событие `pepa.process / finished`. Остановка родителя останавливает ожидаемый дочерний процесс; «Запустить
  сценарий» (без ожидания) создаёт независимый процесс. Вложенность ограничена 8 уровнями.

## D-021. «Для каждого элемента» помнит позицию в памяти блока
- **Почему:** цикл должен переживать перезапуск и не повторять уже обработанные элементы.
- **Последствия:** список фиксируется при входе в цикл и хранится вместе с позицией в памяти процесса. Перебор
  продолжается, только если процесс вернулся в блок из тела цикла; вход тем же путём, что и в первый раз
  (например, следующая итерация внешнего цикла после выхода из внутреннего), начинает перебор заново.

## D-022. Решение о запуске и об отдаче события — в одной транзакции по свежим данным
- **Почему:** ревью этапа 2 нашло гонки: удалённое расписание «воскресало» и продолжало запускаться, событие
  могло достаться двум процессам. Причина одна — решение принималось по данным, прочитанным до транзакции.
- **Последствия:** запуск по расписанию или событию заново читает триггер внутри транзакции, в которой создаётся
  процесс; удалённый, выключенный или изменённый триггер ничего не запускает и не перезаписывается старой копией.
  Событие меняется только из того состояния, в котором его прочитали; всё сопоставление (включая возврат событий
  и решения пользователя) идёт под одним замком. Время шага берётся после получения права записи.

## D-023. События, принятые до перезапуска, и вернувшиеся события не запускают процессы сами
- **Почему:** «после перезапуска ничего не продолжается само» должно касаться и запуска по событиям.
- **Последствия:** событие, принятое до текущего запуска Pepa, сопоставляется с ожидающими процессами, но
  триггеры по нему не срабатывают — до «Сопоставить снова». Событие, которое процесс не применил (завершился,
  повторил шаг, не смог принять), возвращается в «никому не подошло» и предлагается только ожидающим процессам.
  После сбоя платформы во время ожидания доступно «Продолжить» (ожидание цело), а «Выполнить шаг ещё раз»
  снимает прежнее ожидание. Источник `pepa.process` служебный — снаружи его отправить нельзя.

## D-024. Браузер — Playwright с установленными Edge/Chrome, без загрузки своего браузера
- **Почему:** на Windows уже есть Edge; загрузка браузеров Playwright — лишние сотни мегабайт и шаг установки.
- **Последствия:** блок «Открыть браузер» запускает Edge (или Chrome) с отдельным профилем Pepa в папке данных —
  вход на сайты сохраняется, обычный профиль пользователя не трогается; профиль Pepa — ресурс (один процесс за раз).
  Сессия браузера живёт в памяти; после перезапуска Pepa обычный браузер считается закрытым, и блок честно
  останавливается с объяснением. Неоднозначный селектор — ошибка, а не «первый попавшийся». В сборку входит
  Node.js драйвера Playwright только для Windows x64 (~80 МБ).

## D-025. AdsPower — Local API v2 с запасным v1, профиль — ресурс, переподключение без перезапуска профиля
- **Почему:** формат запросов взят из официального клиента AdsPower (`adspower/local-api-mcp-typescript`):
  `POST /api/v2/browser-profile/start|stop`, `GET /api/v2/browser-profile/active`, `POST /api/v2/browser-profile/list`,
  ключ — `Authorization: Bearer`; старые версии AdsPower — `/api/v1/browser/*` и `/api/v1/user/list`.
- **Последствия:** блок «Открыть профиль AdsPower» сам занимает ресурс `adspower:{ID}` и ждёт очереди, если профиль
  у другого процесса. Подключение — Playwright по CDP (`ws.puppeteer` из ответа). После перезапуска Pepa к ещё
  открытому профилю подключается заново (только чтение состояния, ничего не запускается); если профиль закрыт —
  процесс останавливается с объяснением, а не открывает его молча. Запросы к Local API идут по одному с паузой.
  Проверено на имитации Local API; работа с настоящим AdsPower проверяется у пользователя.

## D-026. Telegram — пользовательский аккаунт через MTProto (WTelegramClient), ответы — события
- **Почему:** нужно писать людям и ботам от своего аккаунта и ждать их ответа. Bot API так не умеет (бот не может
  написать первым и не видит чужие чаты), а управление Telegram Desktop мышью ненадёжно. MTProto — официальный
  протокол приложений Telegram; WTelegramClient — зрелая библиотека для .NET без внешних зависимостей.
- **Вход:** один раз в «Интеграциях» (api_id и api_hash с my.telegram.org, телефон, код, пароль двухэтапной проверки);
  в консоли вход не спрашивается никогда. Подключение и каждый шаг входа ограничены по времени (45 с) и прерываются при
  закрытии Pepa; неудачный или брошенный вход не оставляет ни сессии, ни зависшего потока библиотеки. api_hash и
  случайный ключ шифрования сессии в Windows защищены DPAPI (для текущего пользователя).
- **Входящие:** сообщения становятся событиями `telegram / message` с ключом чата `user:123`, `chat:45`, `channel:67`
  и ключом от повторов `{аккаунт}:{чат}:{номер сообщения}`; время события — время сообщения. Библиотека продвигает своё
  состояние обновлений раньше, чем вызывает обработчик, поэтому состояние сохраняется отдельно от обработчика (вскоре
  после подключения, после принятых сообщений, раз в 5 минут, при закрытии) и только если все сообщения приняты движком:
  сообщение, которое не удалось принять (после нескольких попыток), придёт снова после перезапуска, а не пропадёт.
  Файлы пишутся целиком (временный файл и замена); повреждённое состояние — предупреждение, а не отказ работать.
- **Окно ожидания:** событие подходит ожиданию, если произошло во время него: приём — по часам компьютера, время
  источника — с допуском минута на расхождение часов. Догруженное после перезапуска старое сообщение не становится
  «ответом» на новый вопрос, а ответ, пришедший вовремя, пока Pepa была закрыта, принимается. Тайм-аут, истёкший при
  закрытой Pepa, наступает не раньше чем через минуту после запуска — чтобы Telegram успел догрузить сообщения.
  Как и все процессы, ждущие процессы после перезапуска приостановлены и получают такие сообщения после «Продолжить»;
  запуск по ним сам не выполняется (как D-023).
- **Отправка:** до отправки Pepa запоминает номер последнего сообщения чата и ключ от повторов (random_id). Если итог
  неизвестен, проверка ищет своё сообщение (тот же текст, без учёта пробелов по краям) только среди более новых — без
  опоры на часы и без ограничения «последние 30»; подтверждённая проверкой отправка заполняет переменную так же, как
  обычная. Отказ Telegram (нет прав, блокировка, слишком длинное, ограничение частоты) — понятная ошибка «не
  отправлено», а не «итог неизвестен». Ограничение: если за время сбоя тот же текст в тот же чат отправит кто-то ещё
  с этого аккаунта, проверка примет его за своё.
- **Связь:** один цикл переподключения с растущей паузой (10 с … 5 мин); отозванная сессия во время работы переводит к
  повторному входу; поиск чата по @имени кэшируется (Telegram строго ограничивает его частоту).
- Проверено на имитации, на настоящем менеджере обновлений библиотеки без сети и на недоступном сервере; настоящий вход
  проверяется у пользователя.

## D-027. Файл в поле загрузки передаётся содержимым, а не путём
- **Почему:** если в пути есть не латинские буквы (обычное дело: «Документы», «сканы»), Chromium молча оставляет
  поле пустым, а Playwright сообщает об успехе. Это найдено тестом на настоящем браузере.
- **Последствия:** «Прикрепить файл» читает файл (до 50 МБ) и передаёт его браузеру с исходным именем; больший файл —
  только по латинскому пути, иначе понятная ошибка. После выбора блок проверяет, что файл действительно в поле,
  и честно сообщает «итог неизвестен», если его там нет.

## D-028. Окна Windows — UI Automation через FlaUI; мышь и клавиатура — общий ресурс
- **Почему:** UI Automation — штатный способ Windows находить кнопки и поля других программ; FlaUI (UIA3) — проверенная
  обёртка над ним, своя COM-обвязка была бы источником ошибок. Блоки и их логика (поиск, ожидание, неоднозначность,
  проверка результата) живут в переносимом модуле `Pepa.Adapters.Desktop` за интерфейсом `IDesktop` и проверяются на
  имитации; сама работа с Windows — в `Pepa.Adapters.Desktop.Windows` и подключается только оконным приложением.
- **Последствия:** элемент ищется по подписи (целиком или частью), коду AutomationId и типу; несколько подходящих окон
  или элементов — ошибка, а не «первое попавшееся» (кроме явного «взять первый/последний»). Нажатие — без мыши
  (Invoke/Toggle/Select), если программа позволяет, иначе мышью в центр элемента; ввод — через Value pattern, иначе
  клавиатурой. Текст печатается символами Unicode (SendInput), поэтому не зависит от раскладки. Все блоки, которые
  трогают мышь, клавиатуру или передний план, занимают ресурс `desktop:input`: два процесса никогда не смешивают ввод;
  остановившийся с ошибкой процесс держит его до решения пользователя. «Ввести в окне» после сбоя проверяется чтением
  поля, «Закрыть окно» — наличием окна, «Запустить программу» — появлением окна; нажатие и «Клавиатура» не проверяемы —
  после сбоя решение за пользователем. Окна самой Pepa в поиске не участвуют. В сервере без окна блоки есть в
  конструкторе, но при запуске честно сообщают, что работают только в Pepa.exe.

## D-029. Отладка — пауза перед блоком как обычная пауза процесса
- **Почему:** отладка не должна вводить второй способ исполнения: процесс на точке останова — это приостановленный
  процесс (как пауза пользователем), он переживает перезапуск и продолжается только по команде.
- **Последствия:** настройка блока «Пауза перед блоком» и запуск «Пошагово» останавливают процесс перед выполнением
  блока (до вычисления параметров и до действия). Маркер «пауза уже была» (маркер шага и номер шага) хранится в процессе:
  «Продолжить» выполняет этот блок, повторы после ошибки не останавливаются, в цикле пауза — при каждом проходе.
  «Продолжить без остановок» выключает паузы для этого процесса. Запуски по расписанию и событию не пошаговые;
  точки останова в сценарии действуют и на них — это осознанный выбор пользователя при отладке.

## D-030. Запись действий — скрипт на странице и настоящие события, не «запись экрана»
- **Почему:** блоку нужен селектор элемента, а не координаты; браузер сам знает, что нажато и введено.
- **Последствия:** Pepa открывает браузер Pepa (профиль «main») или профиль AdsPower и добавляет на страницы скрипт,
  который слушает только настоящие (isTrusted) нажатия, ввод, выбор, флажки и клавиши Enter/Escape в главной рамке.
  Ввод в поле собирается в один шаг. Селектор — самый устойчивый: id (кроме похожих на сгенерированные), data-testid,
  name, aria-label, placeholder, текст кнопки/ссылки (`button:text-is("…")`), href; путь по положению — последний
  вариант, с пометкой «проверьте». Переход записывается, только если адрес ввёл пользователь (тип перехода сообщает
  браузер), — переходы по ссылкам и перенаправления сайта следуют из нажатий, а их адреса бывают одноразовыми.
  Пароли не записываются: в блок подставляется переменная `password` (вводится при запуске). Профиль, занятый
  процессом, для записи не открывается. Записанное вставляется в сценарий цепочкой блоков, начиная с «Открыть браузер»
  или «Открыть профиль AdsPower».

## D-031. Ввод мышью и клавиатурой — только в окно, которое действительно впереди
- **Почему:** Windows может отказать в выводе окна на передний план (пользователь работает в другом окне), а FlaUI не
  сообщает об этом; без проверки текст или пароль ушёл бы в чужое окно. Ввод в программу, запущенную от имени
  администратора, Windows молча отбрасывает. Центр элемента «по памяти» у прокрученного или перекрытого элемента
  попадает в другое окно.
- **Последствия:** перед каждым вводом (и перед каждым символом текста) Pepa проверяет, что впереди нужное окно (или его
  собственный диалог) и что его программа не запущена с более высокими правами; иначе ввод не выполняется, шаг —
  «не выполнено» (повтор безопасен). Если окно ушло назад посреди набора — «итог неизвестен». Нажатие мышью берёт
  точку элемента заново, прокручивает к нему и проверяет, что в этой точке именно он; «Мышь: нажать в точке» считает
  координаты от окна после разворачивания и проверяет, что точка принадлежит окну. Многострочный текст в «Ввести в окне»
  клавиатурой не печатается (Enter мог бы отправить форму). Нажатие без мыши, на которое программа не отвечает 3 с
  (открылся диалог), считается выполненным с пометкой. UI Automation работает в собственном потоке с тайм-аутами.
  «Запустить программу» ждёт и проверяет новое окно (окно, открытое до запуска, — пометка или решение пользователя),
  «Закрыть окно» не считает успехом окно, которого не было, «Ждать, пока исчезнет» требует, чтобы окно было найдено.

## D-032. Повтор шага видит снимок прошлой попытки; «итог неизвестен» может быть уже проверенным
- **Почему:** библиотека Telegram после обрыва переотправляет запрос сама, и сообщение первой попытки может дойти позже,
  чем проверка сказала «не отправлено». Блок «флажок» или «файл» сам сверяется со страницей — немедленная повторная
  сверка дала бы тот же ответ «не видно», и движок повторил бы действие (флажок снят обратно, файл загружен дважды).
- **Последствия:** при повторе движок передаёт блоку снимок предыдущей попытки (`PreviousCheckpoint`): отправка в Telegram
  повторяет ключ от дублей (`random_id`) и отметку истории, поэтому второе сообщение Telegram не примет
  (`RANDOM_ID_DUPLICATE` = «уже отправлено, проверить»), а проверка найдёт первое. `NodeResult.Unknown` с
  `AlreadyChecked` идёт сразу к пользователю, без автоматической сверки. «Отметить флажок» ждёт до 3 с, пока сайт
  поставит отметку; пустое поле файла после выбора — «неизвестно» (сайт мог забрать файл). Подготовка шага (снимок «до»)
  ограничена тайм-аутом действия.

## D-033. Время событий Telegram — по часам компьютера; тайм-ауты ждут догрузки источника
- **Почему:** окно ожидания и правило «пришедшие, пока Pepa была закрыта, не запускают процессы» сравнивают время
  сообщения (часы Telegram) с часами компьютера; если они расходятся, свежий ответ можно принять за старый и наоборот.
  Тайм-аут, истекающий вскоре после запуска, мог наступить раньше, чем Telegram догрузит ответ, пришедший вовремя.
- **Последствия:** при подключении Pepa сверяет часы с Telegram (`updates.getState`) и переводит время сообщений на
  часы компьютера; расхождение больше 2 минут показывается в состоянии подключения. Источник, который после запуска
  догружает пропущенное (Telegram с сохранённым входом), отмечается в движке: тайм-ауты ожиданий, начатых до запуска,
  наступают не раньше чем через минуту после запуска и не раньше, чем источник догрузит пропущенное (Telegram сообщает
  об этом после загрузки списка чатов и окончания догрузки), — но не позже 10 минут. Записи библиотеки о пропуске
  обновлений («пропущено слишком много», упавший запрос пропущенного, неустранимый разрыв) показываются в состоянии
  подключения; после временных сбоев состояние не сохраняется — после перезапуска библиотека запросит пропущенное снова.
  При закрытии Pepa сначала останавливается движок (выполняющаяся отправка успевает завершиться), потом Telegram.

## D-034. Код JavaScript получает переменные данными, а не текстом
- **Почему:** подстановка `{{ }}` в код делала текст из сообщения кодом на странице с вашим входом.
- **Последствия:** поле «Код» блока «Выполнить JavaScript» — новый вид поля `code`: без подстановок; переменные доступны
  как `vars.имя` (странице передаются только упомянутые в коде). Сценарий с `{{ }}` в коде не проходит проверку с
  понятной подсказкой.

## D-035. ИИ-помощник — Claude API со структурированным ответом и той же проверкой
- **Почему:** помощник должен предлагать только то, что конструктор умеет показать и проверить; свободный текст
  модели пришлось бы угадывать. Ключ — пользовательский: Pepa локальная, своих серверов у неё нет.
- **Последствия:** `Pepa.Assistant` строит указания из реестра блоков (тот же каталог, что в конструкторе: поля, виды
  полей, выходы, правила Pepa) плюс два примера; ответ модели ограничен JSON-схемой (structured outputs): типы блоков —
  перечисление из реестра, поля — список «поле = значение». Черновик приводится к видам полей, получает значения по
  умолчанию и проверяется `ScenarioValidator` как вставленный после «Начала»; ошибки отправляются модели на
  исправление (до 2 раз), оставшиеся показываются пользователю. Помощник ничего не запускает и не сохраняет.
  Модель — `claude-opus-5-5`, effort `high`; указания кешируются (повторные запросы дешевле); включена серверная
  запасная модель (`fallbacks: "default"`, бета `server-side-fallback-2026-07-01`): отказ по правилам безопасности
  повторяется на подходящей модели. Отказ, обрезанный ответ, неверный ключ, лимиты и недоступность сервиса —
  понятные сообщения. Ключ хранится в базе зашифрованным (DPAPI, общий `Pepa.Core.Security.Secrets`) и наружу не
  отдаётся. В Anthropic уходят описание, имена и описания переменных сценария и каталог блоков — не данные процессов.

## D-036. Параллельные ветви — несколько маркеров процесса и структурное слияние
- **Почему:** главный сценарий пользователя — «ждать ответ в Telegram, пока работаешь на сайте»; это две ветви одного
  процесса. Свободные связи «из одного выхода в два блока» сделали бы неясным, когда процесс закончен и чего ждать.
- **Последствия:** «Параллельно» создаёт маркер на каждую подключённую ветвь (2–4) и записывает в маркеры участок
  (id и число ветвей); «Дождаться всех ветвей» продолжает процесс, только когда пришли все ветви своего участка.
  Проверка схемы требует, чтобы ветви сходились в одном слиянии, не сливались раньше и чтобы в середину участка нельзя
  было войти снаружи; «Завершение» можно делить. Шаги ветвей выполняются по очереди одним исполнителем процесса (общие
  переменные и ресурсы без гонок), одновременно идут ожидания (сообщения, события, время, ресурсы). Ошибка в ветви
  останавливает весь процесс; решение пользователя («Повторить», «Пропустить», «Проверить») относится к ветви, которая
  остановилась. Событие для ветви, пришедшее, пока процесс ждёт решения, назначается ей и применяется после
  продолжения. «Завершение» в одной ветви заканчивает процесс: ожидания других ветвей снимаются, их шаги отменяются.

## D-037. Кнопки ботов, файлы и вложения Telegram — по тексту, без угадывания и без слепых повторов
- **Почему:** боты магазинов и сервисов отвечают кнопками и файлами; сценарию «дождаться ответа и нажать
  „Подтвердить“» или «сохранить присланный чек» нужны отдельные блоки, и каждый должен вести себя так же строго,
  как отправка сообщения.
- **Последствия:** «Нажать кнопку в Telegram» ищет кнопку по тексту (целиком или «содержит») в указанном сообщении
  или в последнем сообщении чата с кнопками; несколько подходящих или ни одной — остановка с перечнем кнопок. Перед
  нажатием в снимок шага записываются сообщение и кнопка; если бот успел их поменять — ничего не нажимается. Кнопка
  под сообщением отправляет боту нажатие (ответ бота сохраняется); после сбоя по истории чата нажатие не видно, поэтому
  решение — за пользователем. Кнопка клавиатуры бота отправляет свой текст как сообщение — с тем же ключом от повторов
  и проверкой по истории, что и «Отправить сообщение». Кнопка-ссылка не открывается: адрес сохраняется с
  предупреждением. Кнопки оплаты, игр, запроса телефона и требующие пароль Pepa не нажимает. «Отправить сообщение»
  умеет отправить файл из рабочей папки (подпись — до 1024 символов); загрузка файла ещё не отправка, а потерянное
  подтверждение проверяется по имени файла и подписи. «Сохранить вложение» пишет файл во временный и заменяет целевой
  целиком, поэтому повтор безопасен и после сбоя Pepa сохраняет заново, а не принимает за результат прежний файл с тем же
  именем. Имя файла от собеседника очищается (без папок, «..», символов и имён, недопустимых в Windows). Событие
  «Telegram: сообщение» несёт кнопки и сведения о вложении.

## D-038. Прокси для Telegram — SOCKS5 своим кодом, MTProxy средствами библиотеки; без тихого перехода «напрямую»
- **Почему:** в части сетей Telegram недоступен напрямую; пользователю нужен прокси, который он уже использует в
  Telegram (ссылка tg://proxy или tg://socks) или купил у поставщика (socks5://).
- **Последствия:** прокси задаётся в «Интеграции» → Telegram → «Прокси» ссылкой или полями и проверяется до
  сохранения (SOCKS5 — соединением через него с сервером Telegram, MTProxy — что прокси отвечает). SOCKS5 (RFC 1928,
  вход по логину и паролю — RFC 1929) реализован в `Socks5Connector` и подключён к библиотеке как обработчик
  TCP-соединений: через прокси идут все соединения, в том числе к другим серверам Telegram за файлами, а имя сервера
  разрешает сам прокси. MTProxy передаётся библиотеке ссылкой. Пароль и секрет хранятся зашифрованными (DPAPI) в
  `telegram/proxy.json` и наружу не отдаются; пустое поле при том же прокси оставляет сохранённое значение. После
  сохранения Pepa сразу переподключается через новый прокси; начатый вход прерывается (его нужно пройти заново).
  Если файл настроек прокси не прочитался, Pepa не подключается к Telegram напрямую — пользователь просил прокси, —
  а показывает причину, пока прокси не задан заново. Ошибки прокси называют его и причину (недоступен, не принял
  логин, не соединился с Telegram). Оборванное во время входа соединение — понятная ошибка и форма входа, а не
  зависшее «Подключение…».

## D-039. Итоги шестой проверки: строже там, где итог нельзя подтвердить
- **Почему:** проверка нашла места, где Pepa могла продолжить «как будто получилось» или действовать не там.
- **Последствия:** «Нажать в окне» без мыши, на которое программа не ответила, считается выполненным, только если
  программа открыла новое окно; иначе — «итог неизвестен». Ввод с клавиатуры и мышью — только в то самое окно, о котором
  шаг: диалог программы поверх него останавливает ввод, а печать останавливается, если фокус ушёл в другое поле.
  Завершение процесса (в том числе в другой параллельной ветви) останавливает сценарии, которых он ждал. Снимок
  прошлой попытки — последний из текущего посещения блока: неудачная подготовка не меняет ключ от повторов, следующий
  проход цикла получает новый. Место в очереди ресурса — у ветви; процесс, у которого работает другая ветвь, остаётся в
  очереди активным. Ветви выполняются поочерёдно, а ожидания событий и ресурсов проверяются после каждого шага других
  ветвей. Параллельные ветви не могут работать с одним окном браузера (проверка схемы); общий обработчик ошибок,
  ведущий только к «Завершению», ветви делить могут. «Выполнить JavaScript» выполняет выражения и инструкции как написаны
  (функцию — с переменными аргументом); ошибка записи кода — обычная ошибка «код не выполнялся». Ответ Telegram «уже
  отправлено» (тот же ключ) — успешная отправка, а не повод отправлять снова. Поправка часов Telegram измеряется сразу
  после подключения и следует за переводом часов Windows. Помощник повторяет запрос только при перегрузке или
  внутренней ошибке сервиса, но не после тайм-аута (ответ мог быть дописан и оплачен).
