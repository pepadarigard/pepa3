# Архитектурные решения

Формат: решение → почему → последствия. Новые решения добавляются в конец; отменённые не удаляются, а помечаются.

## D-001. C# и .NET 10 (LTS)
- **Почему:** нативный доступ к Windows (UI Automation, SendInput, WebView2), зрелая экосистема, долгая поддержка.
- **Последствия:** все проекты, кроме оболочки, — `net10.0` (собираются и тестируются на любой ОС);
  оболочка — `net10.0-windows`.

## D-002. Модульный монолит из небольшого числа проектов
- **Почему:** 13 модулей из ТЗ — это границы ответственности, а не обязательно отдельные сборки. Лишние проекты
  дают церемонии без пользы.
- **Последствия:** проекты `Core`, `Engine`, `Storage.Sqlite`, `Adapters.*`, `Host`, `Server`, `Desktop`.
  Направление зависимостей строго одно: `Core ← Engine ← (Storage, Adapters) ← Host ← (Server, Desktop)`.
  Модуль выносится в отдельный проект, когда появляется реальная причина (своя зависимость, своя платформа).

## D-003. Интерфейс целиком на React внутри WebView2, WPF — тонкая оболочка
- **Почему:** один UI-стек вместо двух; конструктор и история показывают одну и ту же схему; веб-интерфейс
  можно проверять автоматически (Playwright) на любой ОС, в том числе там, где ведётся разработка.
- **Последствия:** WPF отвечает за окно, жизненный цикл, нативные функции (выбор папки, открыть в проводнике,
  в будущем — трей, горячие клавиши, оверлеи записи и выбора элементов). WebView2 Runtime есть в Windows 10/11.

## D-004. Мост «интерфейс ↔ движок» — локальный HTTP API, а не postMessage
- **Почему:** один и тот же API работает в WebView2, в обычном браузере (разработка, тесты) и в будущем —
  для удалённого просмотра. Нет двух реализаций моста.
- **Безопасность:** Kestrel слушает только `127.0.0.1`, случайный порт; каждый запрос к `/api` требует
  случайный токен в заголовке `X-Pepa-Token`; проверяется заголовок `Host` (защита от DNS rebinding).
  Сторонний сайт в браузере не может прочитать токен и не может вызвать API.
- **Последствия:** нативные функции, которых нет в браузере, идут через `chrome.webview.postMessage`
  и в обычном браузере просто скрыты.

## D-005. Сценарий — граф узлов и связей; исполнение через «маркеры»
- **Почему:** граф естественно описывает ветвления, циклы (обратные связи), ожидания и в будущем — параллельные
  ветви; состояние процесса = где стоят маркеры + переменные; это легко сохранять и восстанавливать.
  React Flow рисует такой граф напрямую. Запись действий даёт линейную цепочку в том же формате.
- **Последствия:** у каждого выходного порта ровно одна связь (никакого неявного параллелизма). Параллельность
  появится только через явные узлы «разделение/слияние» со структурной проверкой. Формат версионируется
  (`schemaVersion`).

## D-006. Надёжность исполнения — в ядре с первого этапа (изменение порядка этапов ТЗ)
- **Почему:** если сделать движок «в памяти», на этапе 2 его пришлось бы переписывать.
- **Последствия:** уже в первой версии каждый шаг проходит состояния «запланирован → выполняется →
  подтверждён / не выполнен / неизвестно / ожидает», а переход в «выполняется» записывается на диск до вызова
  внешнего действия. Ожидание — запись в базе, а не спящий поток.

## D-007. Снимок состояния + журнал, а не полноценный event sourcing
- **Почему:** сценарий — интерпретируемые данные, а не пользовательский код, поэтому нет нужды «переигрывать»
  историю, как в Temporal. Снимок проще, журнал даёт историю и диагностику.
- **Последствия:** таблицы `processes`, `tokens`, `steps`, `logs`; каждый переход — одна транзакция.

## D-008. SQLite через Microsoft.Data.Sqlite, без ORM
- **Почему:** полный контроль над транзакциями и схемой, мало зависимостей.
- **Последствия:** WAL, `synchronous=FULL` (запись о начале внешнего действия не теряется при сбое питания),
  все записи сериализованы одним замком; миграции по `PRAGMA user_version`. Скорость при этом достаточна:
  десятки и сотни шагов в секунду.

## D-009. Выражения — JavaScript (Jint) в песочнице
- **Почему:** синтаксис знаком пользователям и ИИ; есть строки, регулярные выражения, даты, JSON. Свой язык
  дольше и всё равно упёрся бы в эти потребности.
- **Последствия:** лимиты времени, памяти, рекурсии и числа операций; нет доступа к .NET, файлам и сети.
  Условие обязано вернуть `true/false` (строгая проверка вместо «правдоподобных» значений).
  Шаблоны строк: `Привет, {{ vars.name }}`.

## D-010. Восстановление консервативно; результат внешних действий сверяется, а не повторяется
- **Почему:** требование ТЗ — не повторять действие с неизвестным результатом.
- **Последствия:** у действия есть необязательные `Prepare` (снимок «до») и `Verify` (проверка «выполнилось ли»).
  После перезапуска процессы приостановлены; шаг, прерванный посреди выполнения, получает статус «неизвестно».
  При ручном возобновлении сначала выполняется проверка; если она невозможна или неоднозначна — решает пользователь.

## D-011. Базовый визуальный конструктор — уже на первом этапе (изменение порядка этапов ТЗ)
- **Почему:** интерфейс веб-ориентированный (D-003), конструктор на React Flow не требует отдельной
  инфраструктуры, а без него пользователь не может удобно создавать и проверять сценарии.
- **Последствия:** этап 3 становится «развитием конструктора» (подпроцессы, параллельные ветви, отладка по шагам и т.д.).

## D-012. Разработка в облачном Linux-контейнере, проверка Windows — через GitHub Actions
- **Почему:** так работа не зависит от того, включён ли ПК пользователя.
- **Последствия:** всё, кроме оболочки, собирается и тестируется в контейнере; оболочка компилируется там же
  (`EnableWindowsTargeting`). Сборка и тесты на Windows и готовый архив приложения — в GitHub Actions.

## D-013. Один экземпляр на папку данных
- **Почему:** два экземпляра над одной базой исполнили бы одни и те же шаги дважды.
- **Последствия:** эксклюзивная блокировка файла `instance.lock` в папке данных на всё время работы.

## D-014. Файловые действия ограничены рабочей папкой
- **Почему:** первое действие должно быть безопасным; ошибка в пути не должна задеть чужие файлы.
- **Последствия:** любые пути разрешаются относительно рабочей папки; выход за её пределы (`..`, абсолютные пути,
  ссылки/junction) запрещён. Это основа будущей системы разрешений.

## D-015. Интерфейс на русском, строки отдельно от кода
- **Последствия:** тексты интерфейса — в `ui/src/i18n`; сообщения движка и проверки — с кодом и русским текстом.

## D-016. Событие применяет сам процесс, а не маршрутизатор
- **Почему:** состояние процесса меняет только его владелец (`ProcessSlot`). Маршрутизатор лишь назначает событие
  подписке (атомарная смена «ждёт → получено» в хранилище), а процесс применяет его своим обычным шагом.
- **Последствия:** событие для приостановленного или требующего решения процесса остаётся «назначенным» и
  применяется только после возобновления. Если процесс завершился, не применив событие, оно возвращается на
  сопоставление. Сопоставление идёт по одному событию за раз (замок маршрутизатора), в порядке поступления.

## D-017. Неоднозначность — не угадываем
- **Почему:** ТЗ требует не выполнять незапланированных действий.
- **Последствия:** если событие одинаково подходит нескольким процессам (одинаковый наивысший приоритет), оно
  получает состояние «нужно решение» и не отдаётся никому; пользователь выбирает получателя или пропускает событие.
  Событие, которое никто не ждёт и не запускает триггер, сохраняется как «никому не подошло». Процессы,
  начавшие ждать позже, могут забрать его, только если явно разрешили окно «пришедшие раньше».
  Ключ сопоставления, который задан, но получился пустым (не заполнена переменная), — ошибка шага, а не «любой ключ».

## D-018. Ресурсы: очередь по порядку, приостановленные пропускаются, но сохраняют место
- **Почему:** ожидание не должно блокировать других (ТЗ), а приостановленный процесс не может воспользоваться
  ресурсом. Отдавать ресурс процессу на паузе — значит держать его впустую.
- **Последствия:** при освобождении ресурс получает первый в очереди процесс в состоянии «ожидает». Ресурсы
  приостановленного процесса остаются за ним (он мог оставить профиль открытым) — освободить можно вручную.
  Взаимная блокировка (процесс ждёт ресурс у того, кто ждёт его ресурс) обнаруживается при запросе и
  останавливает запросивший процесс с объяснением. После сбоя ресурсы завершённых процессов освобождаются.

## D-019. Расписания без cron; пропущенное не запускается само
- **Почему:** понятность для пользователя важнее выразительности; ТЗ запрещает автозапуск после перезапуска.
- **Последствия:** три вида расписания: каждые N минут (от местной полуночи), по дням недели, один раз. Каждый
  запуск имеет ключ происхождения (`schedule:{триггер}:{время}`, `event:{триггер}:{событие}`), уникальный в базе, —
  двойной запуск невозможен. Пока Pepa была закрыта, запуски считаются пропущенными и показываются на главной.
  «Не запускать, пока работает предыдущий» включено по умолчанию. Событие, которое ждёт работающий процесс,
  достаётся ему, а не триггеру. Запуск, опоздавший больше чем на 10 минут при открытом приложении (например,
  компьютер спал), тоже считается пропущенным. Интервал, укладывающийся в сутки, отсчитывается от местной
  полуночи, остальные — ровной сеткой без сбоя в полночь.

## D-020. Вызов сценария: дочерний процесс, итог — событием
- **Почему:** дочерний процесс — полноценный процесс со своим состоянием, журналом и восстановлением; ожидание
  его итога — то же ожидание события (без отдельного механизма).
- **Последствия:** «Вызвать сценарий» создаёт дочерний процесс в той же транзакции, что и шаг, и ждёт служебное
  событие `pepa.process / finished`. Остановка родителя останавливает ожидаемый дочерний процесс; «Запустить
  сценарий» (без ожидания) создаёт независимый процесс. Вложенность ограничена 8 уровнями.

## D-021. «Для каждого элемента» помнит позицию в памяти блока
- **Почему:** цикл должен переживать перезапуск и не повторять уже обработанные элементы.
- **Последствия:** список фиксируется при входе в цикл и хранится вместе с позицией в памяти процесса. Перебор
  продолжается, только если процесс вернулся в блок из тела цикла; вход тем же путём, что и в первый раз
  (например, следующая итерация внешнего цикла после выхода из внутреннего), начинает перебор заново.

## D-022. Решение о запуске и об отдаче события — в одной транзакции по свежим данным
- **Почему:** ревью этапа 2 нашло гонки: удалённое расписание «воскресало» и продолжало запускаться, событие
  могло достаться двум процессам. Причина одна — решение принималось по данным, прочитанным до транзакции.
- **Последствия:** запуск по расписанию или событию заново читает триггер внутри транзакции, в которой создаётся
  процесс; удалённый, выключенный или изменённый триггер ничего не запускает и не перезаписывается старой копией.
  Событие меняется только из того состояния, в котором его прочитали; всё сопоставление (включая возврат событий
  и решения пользователя) идёт под одним замком. Время шага берётся после получения права записи.

## D-023. События, принятые до перезапуска, и вернувшиеся события не запускают процессы сами
- **Почему:** «после перезапуска ничего не продолжается само» должно касаться и запуска по событиям.
- **Последствия:** событие, принятое до текущего запуска Pepa, сопоставляется с ожидающими процессами, но
  триггеры по нему не срабатывают — до «Сопоставить снова». Событие, которое процесс не применил (завершился,
  повторил шаг, не смог принять), возвращается в «никому не подошло» и предлагается только ожидающим процессам.
  После сбоя платформы во время ожидания доступно «Продолжить» (ожидание цело), а «Выполнить шаг ещё раз»
  снимает прежнее ожидание. Источник `pepa.process` служебный — снаружи его отправить нельзя.

## D-024. Браузер — Playwright с установленными Edge/Chrome, без загрузки своего браузера
- **Почему:** на Windows уже есть Edge; загрузка браузеров Playwright — лишние сотни мегабайт и шаг установки.
- **Последствия:** блок «Открыть браузер» запускает Edge (или Chrome) с отдельным профилем Pepa в папке данных —
  вход на сайты сохраняется, обычный профиль пользователя не трогается; профиль Pepa — ресурс (один процесс за раз).
  Сессия браузера живёт в памяти; после перезапуска Pepa обычный браузер считается закрытым, и блок честно
  останавливается с объяснением. Неоднозначный селектор — ошибка, а не «первый попавшийся». В сборку входит
  Node.js драйвера Playwright только для Windows x64 (~80 МБ).

## D-025. AdsPower — Local API v2 с запасным v1, профиль — ресурс, переподключение без перезапуска профиля
- **Почему:** формат запросов взят из официального клиента AdsPower (`adspower/local-api-mcp-typescript`):
  `POST /api/v2/browser-profile/start|stop`, `GET /api/v2/browser-profile/active`, `POST /api/v2/browser-profile/list`,
  ключ — `Authorization: Bearer`; старые версии AdsPower — `/api/v1/browser/*` и `/api/v1/user/list`.
- **Последствия:** блок «Открыть профиль AdsPower» сам занимает ресурс `adspower:{ID}` и ждёт очереди, если профиль
  у другого процесса. Подключение — Playwright по CDP (`ws.puppeteer` из ответа). После перезапуска Pepa к ещё
  открытому профилю подключается заново (только чтение состояния, ничего не запускается); если профиль закрыт —
  процесс останавливается с объяснением, а не открывает его молча. Запросы к Local API идут по одному с паузой.
  Проверено на имитации Local API; работа с настоящим AdsPower проверяется у пользователя.

## D-026. Telegram — пользовательский аккаунт через MTProto (WTelegramClient), ответы — события
- **Почему:** нужно писать людям и ботам от своего аккаунта и ждать их ответа. Bot API так не умеет (бот не может
  написать первым и не видит чужие чаты), а управление Telegram Desktop мышью ненадёжно. MTProto — официальный
  протокол приложений Telegram; WTelegramClient — зрелая библиотека для .NET без внешних зависимостей.
- **Вход:** один раз в «Интеграциях» (api_id и api_hash с my.telegram.org, телефон, код, пароль двухэтапной проверки);
  в консоли вход не спрашивается никогда. Подключение и каждый шаг входа ограничены по времени (45 с) и прерываются при
  закрытии Pepa; неудачный или брошенный вход не оставляет ни сессии, ни зависшего потока библиотеки. api_hash и
  случайный ключ шифрования сессии в Windows защищены DPAPI (для текущего пользователя).
- **Входящие:** сообщения становятся событиями `telegram / message` с ключом чата `user:123`, `chat:45`, `channel:67`
  и ключом от повторов `{аккаунт}:{чат}:{номер сообщения}`; время события — время сообщения. Библиотека продвигает своё
  состояние обновлений раньше, чем вызывает обработчик, поэтому состояние сохраняется отдельно от обработчика (вскоре
  после подключения, после принятых сообщений, раз в 5 минут, при закрытии) и только если все сообщения приняты движком:
  сообщение, которое не удалось принять (после нескольких попыток), придёт снова после перезапуска, а не пропадёт.
  Файлы пишутся целиком (временный файл и замена); повреждённое состояние — предупреждение, а не отказ работать.
- **Окно ожидания:** событие подходит ожиданию, если произошло во время него: приём — по часам компьютера, время
  источника — с допуском минута на расхождение часов. Догруженное после перезапуска старое сообщение не становится
  «ответом» на новый вопрос, а ответ, пришедший вовремя, пока Pepa была закрыта, принимается. Тайм-аут, истёкший при
  закрытой Pepa, наступает не раньше чем через минуту после запуска — чтобы Telegram успел догрузить сообщения.
  Как и все процессы, ждущие процессы после перезапуска приостановлены и получают такие сообщения после «Продолжить»;
  запуск по ним сам не выполняется (как D-023).
- **Отправка:** до отправки Pepa запоминает номер последнего сообщения чата и ключ от повторов (random_id). Если итог
  неизвестен, проверка ищет своё сообщение (тот же текст, без учёта пробелов по краям) только среди более новых — без
  опоры на часы и без ограничения «последние 30»; подтверждённая проверкой отправка заполняет переменную так же, как
  обычная. Отказ Telegram (нет прав, блокировка, слишком длинное, ограничение частоты) — понятная ошибка «не
  отправлено», а не «итог неизвестен». Ограничение: если за время сбоя тот же текст в тот же чат отправит кто-то ещё
  с этого аккаунта, проверка примет его за своё.
- **Связь:** один цикл переподключения с растущей паузой (10 с … 5 мин); отозванная сессия во время работы переводит к
  повторному входу; поиск чата по @имени кэшируется (Telegram строго ограничивает его частоту).
- Проверено на имитации, на настоящем менеджере обновлений библиотеки без сети и на недоступном сервере; настоящий вход
  проверяется у пользователя.

## D-027. Файл в поле загрузки передаётся содержимым, а не путём
- **Почему:** если в пути есть не латинские буквы (обычное дело: «Документы», «сканы»), Chromium молча оставляет
  поле пустым, а Playwright сообщает об успехе. Это найдено тестом на настоящем браузере.
- **Последствия:** «Прикрепить файл» читает файл (до 50 МБ) и передаёт его браузеру с исходным именем; больший файл —
  только по латинскому пути, иначе понятная ошибка. После выбора блок проверяет, что файл действительно в поле,
  и честно сообщает «итог неизвестен», если его там нет.

## D-028. Окна Windows — UI Automation через FlaUI; мышь и клавиатура — общий ресурс
- **Почему:** UI Automation — штатный способ Windows находить кнопки и поля других программ; FlaUI (UIA3) — проверенная
  обёртка над ним, своя COM-обвязка была бы источником ошибок. Блоки и их логика (поиск, ожидание, неоднозначность,
  проверка результата) живут в переносимом модуле `Pepa.Adapters.Desktop` за интерфейсом `IDesktop` и проверяются на
  имитации; сама работа с Windows — в `Pepa.Adapters.Desktop.Windows` и подключается только оконным приложением.
- **Последствия:** элемент ищется по подписи (целиком или частью), коду AutomationId и типу; несколько подходящих окон
  или элементов — ошибка, а не «первое попавшееся» (кроме явного «взять первый/последний»). Нажатие — без мыши
  (Invoke/Toggle/Select), если программа позволяет, иначе мышью в центр элемента; ввод — через Value pattern, иначе
  клавиатурой. Текст печатается символами Unicode (SendInput), поэтому не зависит от раскладки. Все блоки, которые
  трогают мышь, клавиатуру или передний план, занимают ресурс `desktop:input`: два процесса никогда не смешивают ввод;
  остановившийся с ошибкой процесс держит его до решения пользователя. «Ввести в окне» после сбоя проверяется чтением
  поля, «Закрыть окно» — наличием окна, «Запустить программу» — появлением окна; нажатие и «Клавиатура» не проверяемы —
  после сбоя решение за пользователем. Окна самой Pepa в поиске не участвуют. В сервере без окна блоки есть в
  конструкторе, но при запуске честно сообщают, что работают только в Pepa.exe.

## D-029. Отладка — пауза перед блоком как обычная пауза процесса
- **Почему:** отладка не должна вводить второй способ исполнения: процесс на точке останова — это приостановленный
  процесс (как пауза пользователем), он переживает перезапуск и продолжается только по команде.
- **Последствия:** настройка блока «Пауза перед блоком» и запуск «Пошагово» останавливают процесс перед выполнением
  блока (до вычисления параметров и до действия). Маркер «пауза уже была» (маркер шага и номер шага) хранится в процессе:
  «Продолжить» выполняет этот блок, повторы после ошибки не останавливаются, в цикле пауза — при каждом проходе.
  «Продолжить без остановок» выключает паузы для этого процесса. Запуски по расписанию и событию не пошаговые;
  точки останова в сценарии действуют и на них — это осознанный выбор пользователя при отладке.

## D-030. Запись действий — скрипт на странице и настоящие события, не «запись экрана»
- **Почему:** блоку нужен селектор элемента, а не координаты; браузер сам знает, что нажато и введено.
- **Последствия:** Pepa открывает браузер Pepa (профиль «main») или профиль AdsPower и добавляет на страницы скрипт,
  который слушает только настоящие (isTrusted) нажатия, ввод, выбор, флажки и клавиши Enter/Escape в главной рамке.
  Ввод в поле собирается в один шаг. Селектор — самый устойчивый: id (кроме похожих на сгенерированные), data-testid,
  name, aria-label, placeholder, текст кнопки/ссылки (`button:text-is("…")`), href; путь по положению — последний
  вариант, с пометкой «проверьте». Переход записывается, только если адрес ввёл пользователь (тип перехода сообщает
  браузер), — переходы по ссылкам и перенаправления сайта следуют из нажатий, а их адреса бывают одноразовыми.
  Пароли не записываются: в блок подставляется переменная `password` (вводится при запуске). Профиль, занятый
  процессом, для записи не открывается. Записанное вставляется в сценарий цепочкой блоков, начиная с «Открыть браузер»
  или «Открыть профиль AdsPower».

## D-031. Ввод мышью и клавиатурой — только в окно, которое действительно впереди
- **Почему:** Windows может отказать в выводе окна на передний план (пользователь работает в другом окне), а FlaUI не
  сообщает об этом; без проверки текст или пароль ушёл бы в чужое окно. Ввод в программу, запущенную от имени
  администратора, Windows молча отбрасывает. Центр элемента «по памяти» у прокрученного или перекрытого элемента
  попадает в другое окно.
- **Последствия:** перед каждым вводом (и перед каждым символом текста) Pepa проверяет, что впереди нужное окно (или его
  собственный диалог) и что его программа не запущена с более высокими правами; иначе ввод не выполняется, шаг —
  «не выполнено» (повтор безопасен). Если окно ушло назад посреди набора — «итог неизвестен». Нажатие мышью берёт
  точку элемента заново, прокручивает к нему и проверяет, что в этой точке именно он; «Мышь: нажать в точке» считает
  координаты от окна после разворачивания и проверяет, что точка принадлежит окну. Многострочный текст в «Ввести в окне»
  клавиатурой не печатается (Enter мог бы отправить форму). Нажатие без мыши, на которое программа не отвечает 3 с
  (открылся диалог), считается выполненным с пометкой. UI Automation работает в собственном потоке с тайм-аутами.
  «Запустить программу» ждёт и проверяет новое окно (окно, открытое до запуска, — пометка или решение пользователя),
  «Закрыть окно» не считает успехом окно, которого не было, «Ждать, пока исчезнет» требует, чтобы окно было найдено.

## D-032. Повтор шага видит снимок прошлой попытки; «итог неизвестен» может быть уже проверенным
- **Почему:** библиотека Telegram после обрыва переотправляет запрос сама, и сообщение первой попытки может дойти позже,
  чем проверка сказала «не отправлено». Блок «флажок» или «файл» сам сверяется со страницей — немедленная повторная
  сверка дала бы тот же ответ «не видно», и движок повторил бы действие (флажок снят обратно, файл загружен дважды).
- **Последствия:** при повторе движок передаёт блоку снимок предыдущей попытки (`PreviousCheckpoint`): отправка в Telegram
  повторяет ключ от дублей (`random_id`) и отметку истории, поэтому второе сообщение Telegram не примет
  (`RANDOM_ID_DUPLICATE` = «уже отправлено, проверить»), а проверка найдёт первое. `NodeResult.Unknown` с
  `AlreadyChecked` идёт сразу к пользователю, без автоматической сверки. «Отметить флажок» ждёт до 3 с, пока сайт
  поставит отметку; пустое поле файла после выбора — «неизвестно» (сайт мог забрать файл). Подготовка шага (снимок «до»)
  ограничена тайм-аутом действия.

## D-033. Время событий Telegram — по часам компьютера; тайм-ауты ждут догрузки источника
- **Почему:** окно ожидания и правило «пришедшие, пока Pepa была закрыта, не запускают процессы» сравнивают время
  сообщения (часы Telegram) с часами компьютера; если они расходятся, свежий ответ можно принять за старый и наоборот.
  Тайм-аут, истекающий вскоре после запуска, мог наступить раньше, чем Telegram догрузит ответ, пришедший вовремя.
- **Последствия:** при подключении Pepa сверяет часы с Telegram (`updates.getState`) и переводит время сообщений на
  часы компьютера; расхождение больше 2 минут показывается в состоянии подключения. Источник, который после запуска
  догружает пропущенное (Telegram с сохранённым входом), отмечается в движке: тайм-ауты ожиданий, начатых до запуска,
  наступают не раньше чем через минуту после запуска и не раньше, чем источник догрузит пропущенное (Telegram сообщает
  об этом после загрузки списка чатов и окончания догрузки), — но не позже 10 минут. Записи библиотеки о пропуске
  обновлений («пропущено слишком много», упавший запрос пропущенного, неустранимый разрыв) показываются в состоянии
  подключения; после временных сбоев состояние не сохраняется — после перезапуска библиотека запросит пропущенное снова.
  При закрытии Pepa сначала останавливается движок (выполняющаяся отправка успевает завершиться), потом Telegram.

## D-034. Код JavaScript получает переменные данными, а не текстом
- **Почему:** подстановка `{{ }}` в код делала текст из сообщения кодом на странице с вашим входом.
- **Последствия:** поле «Код» блока «Выполнить JavaScript» — новый вид поля `code`: без подстановок; переменные доступны
  как `vars.имя` (странице передаются только упомянутые в коде). Сценарий с `{{ }}` в коде не проходит проверку с
  понятной подсказкой.

## D-035. ИИ-помощник — Claude API со структурированным ответом и той же проверкой
- **Почему:** помощник должен предлагать только то, что конструктор умеет показать и проверить; свободный текст
  модели пришлось бы угадывать. Ключ — пользовательский: Pepa локальная, своих серверов у неё нет.
- **Последствия:** `Pepa.Assistant` строит указания из реестра блоков (тот же каталог, что в конструкторе: поля, виды
  полей, выходы, правила Pepa) плюс два примера; ответ модели ограничен JSON-схемой (structured outputs): типы блоков —
  перечисление из реестра, поля — список «поле = значение». Черновик приводится к видам полей, получает значения по
  умолчанию и проверяется `ScenarioValidator` как вставленный после «Начала»; ошибки отправляются модели на
  исправление (до 2 раз), оставшиеся показываются пользователю. Помощник ничего не запускает и не сохраняет.
  Модель — `claude-opus-5-5`, effort `high`; указания кешируются (повторные запросы дешевле); включена серверная
  запасная модель (`fallbacks: "default"`, бета `server-side-fallback-2026-07-01`): отказ по правилам безопасности
  повторяется на подходящей модели. Отказ, обрезанный ответ, неверный ключ, лимиты и недоступность сервиса —
  понятные сообщения. Ключ хранится в базе зашифрованным (DPAPI, общий `Pepa.Core.Security.Secrets`) и наружу не
  отдаётся. В Anthropic уходят описание, имена и описания переменных сценария и каталог блоков — не данные процессов.

## D-036. Параллельные ветви — несколько маркеров процесса и структурное слияние
- **Почему:** главный сценарий пользователя — «ждать ответ в Telegram, пока работаешь на сайте»; это две ветви одного
  процесса. Свободные связи «из одного выхода в два блока» сделали бы неясным, когда процесс закончен и чего ждать.
- **Последствия:** «Параллельно» создаёт маркер на каждую подключённую ветвь (2–4) и записывает в маркеры участок
  (id и число ветвей); «Дождаться всех ветвей» продолжает процесс, только когда пришли все ветви своего участка.
  Проверка схемы требует, чтобы ветви сходились в одном слиянии, не сливались раньше и чтобы в середину участка нельзя
  было войти снаружи; «Завершение» можно делить. Шаги ветвей выполняются по очереди одним исполнителем процесса (общие
  переменные и ресурсы без гонок), одновременно идут ожидания (сообщения, события, время, ресурсы). Ошибка в ветви
  останавливает весь процесс; решение пользователя («Повторить», «Пропустить», «Проверить») относится к ветви, которая
  остановилась. Событие для ветви, пришедшее, пока процесс ждёт решения, назначается ей и применяется после
  продолжения. «Завершение» в одной ветви заканчивает процесс: ожидания других ветвей снимаются, их шаги отменяются.

## D-037. Кнопки ботов, файлы и вложения Telegram — по тексту, без угадывания и без слепых повторов
- **Почему:** боты магазинов и сервисов отвечают кнопками и файлами; сценарию «дождаться ответа и нажать
  „Подтвердить“» или «сохранить присланный чек» нужны отдельные блоки, и каждый должен вести себя так же строго,
  как отправка сообщения.
- **Последствия:** «Нажать кнопку в Telegram» ищет кнопку по тексту (целиком или «содержит») в указанном сообщении
  или в последнем сообщении чата с кнопками; несколько подходящих или ни одной — остановка с перечнем кнопок. Перед
  нажатием в снимок шага записываются сообщение и кнопка; если бот успел их поменять — ничего не нажимается. Кнопка
  под сообщением отправляет боту нажатие (ответ бота сохраняется); после сбоя по истории чата нажатие не видно, поэтому
  решение — за пользователем. Кнопка клавиатуры бота отправляет свой текст как сообщение — с тем же ключом от повторов
  и проверкой по истории, что и «Отправить сообщение». Кнопка-ссылка не открывается: адрес сохраняется с
  предупреждением. Кнопки оплаты, игр, запроса телефона и требующие пароль Pepa не нажимает. «Отправить сообщение»
  умеет отправить файл из рабочей папки (подпись — до 1024 символов); загрузка файла ещё не отправка, а потерянное
  подтверждение проверяется по имени файла и подписи. «Сохранить вложение» пишет файл во временный и заменяет целевой
  целиком, поэтому повтор безопасен и после сбоя Pepa сохраняет заново, а не принимает за результат прежний файл с тем же
  именем. Имя файла от собеседника очищается (без папок, «..», символов и имён, недопустимых в Windows). Событие
  «Telegram: сообщение» несёт кнопки и сведения о вложении.

## D-038. Прокси для Telegram — SOCKS5 своим кодом, MTProxy средствами библиотеки; без тихого перехода «напрямую»
- **Почему:** в части сетей Telegram недоступен напрямую; пользователю нужен прокси, который он уже использует в
  Telegram (ссылка tg://proxy или tg://socks) или купил у поставщика (socks5://).
- **Последствия:** прокси задаётся в «Интеграции» → Telegram → «Прокси» ссылкой или полями и проверяется до
  сохранения (SOCKS5 — соединением через него с сервером Telegram, MTProxy — что прокси отвечает). SOCKS5 (RFC 1928,
  вход по логину и паролю — RFC 1929) реализован в `Socks5Connector` и подключён к библиотеке как обработчик
  TCP-соединений: через прокси идут все соединения, в том числе к другим серверам Telegram за файлами, а имя сервера
  разрешает сам прокси. MTProxy передаётся библиотеке ссылкой. Пароль и секрет хранятся зашифрованными (DPAPI) в
  `telegram/proxy.json` и наружу не отдаются; пустое поле при том же прокси оставляет сохранённое значение. После
  сохранения Pepa сразу переподключается через новый прокси; начатый вход прерывается (его нужно пройти заново).
  Если файл настроек прокси не прочитался, Pepa не подключается к Telegram напрямую — пользователь просил прокси, —
  а показывает причину, пока прокси не задан заново. Ошибки прокси называют его и причину (недоступен, не принял
  логин, не соединился с Telegram). Оборванное во время входа соединение — понятная ошибка и форма входа, а не
  зависшее «Подключение…».

## D-039. Итоги шестой проверки: строже там, где итог нельзя подтвердить
- **Почему:** проверка нашла места, где Pepa могла продолжить «как будто получилось» или действовать не там.
- **Последствия:** «Нажать в окне» без мыши, на которое программа не ответила, считается выполненным, только если
  программа открыла новое окно; иначе — «итог неизвестен». Ввод с клавиатуры и мышью — только в то самое окно, о котором
  шаг: диалог программы поверх него останавливает ввод, а печать останавливается, если фокус ушёл в другое поле.
  Завершение процесса (в том числе в другой параллельной ветви) останавливает сценарии, которых он ждал. Снимок
  прошлой попытки — последний из текущего посещения блока: неудачная подготовка не меняет ключ от повторов, следующий
  проход цикла получает новый. Место в очереди ресурса — у ветви; процесс, у которого работает другая ветвь, остаётся в
  очереди активным. Ветви выполняются поочерёдно, а ожидания событий и ресурсов проверяются после каждого шага других
  ветвей. Параллельные ветви не могут работать с одним окном браузера (проверка схемы); общий обработчик ошибок,
  ведущий только к «Завершению», ветви делить могут. «Выполнить JavaScript» выполняет выражения и инструкции как написаны
  (функцию — с переменными аргументом); ошибка записи кода — обычная ошибка «код не выполнялся». Ответ Telegram «уже
  отправлено» (тот же ключ) — успешная отправка, а не повод отправлять снова. Поправка часов Telegram измеряется сразу
  после подключения и следует за переводом часов Windows. Помощник повторяет запрос только при перегрузке или
  внутренней ошибке сервиса, но не после тайм-аута (ответ мог быть дописан и оплачен).

## D-040. Группы на схеме — только вид конструктора; «подпроцесс» — вызовом сценария
- **Почему:** большие схемы нужно делить на части и сворачивать, но «свернуть часть схемы в отдельный сценарий»
  автоматически меняло бы поведение: вызванный сценарий — отдельный процесс со своими переменными, без открытого
  браузера и занятых ресурсов вызывающего. Такое незаметное изменение противоречит правилу «никаких незапланированных
  действий».
- **Последствия:** группа (Ctrl+G или кнопка на панели) — рамка с названием вокруг выбранных блоков; её можно
  переименовать (двойной щелчок), передвинуть целиком за заголовок, свернуть в один блок (связи с её блоками показаны от
  него и к нему, ошибки блоков — счётчиком) и разгруппировать. Хранится в данных редактора сценария (`editor.groups`),
  движок её не читает, поэтому на выполнение она не влияет; на странице процесса группы видны рамками. Блок — только в
  одной группе; удалённые блоки уходят из групп; «Выбрать всё» не выбирает блоки свёрнутых групп, а переход к блоку
  из списка ошибок или поиска разворачивает его группу. Вынести часть схемы в отдельный сценарий можно вручную:
  копировать блоки (Ctrl+C), вставить в новый сценарий и вызвать его блоком «Вызвать сценарий».

## D-041. Помощник объясняет и правит сценарий — целиком, с показом изменений до применения
- **Почему:** пользователю нужно понять чужой или старый сценарий и поправить его словами, не разбирая каждый блок.
- **Последствия:** в окне помощника три режима: «Новые блоки», «Изменить сценарий», «Объяснить сценарий». Для правки и
  объяснения модели уходит сценарий в формате ответа помощника (блоки с полями и связи, без «Начала»), имена и описания
  переменных — без их значений; окно говорит об этом прямо. Правка возвращается целиком: неизменённые блоки сохраняют
  id и место на схеме, новые ставятся рядом с блоком, за которым идут. Ответ проходит ту же проверку и исправление, что
  черновик. До применения видно, какие блоки добавятся, изменятся (с названиями полей) и удалятся, и сколько связей
  поменяется; «Применить изменения» — одно изменение схемы (Ctrl+Z отменяет), «Начало» подключается к первому блоку
  правки. Объяснение — по блокам (щелчок показывает блок на схеме) и «что стоит проверить»; сценарий не меняется.

## D-042. Итоги седьмой проверки: нажатие кнопки бота — не больше одного раза
- **Почему:** библиотека Telegram после обрыва связи сама переподключается и повторяет запросы, которые ждали ответа, а
  на ответ «-503» повторяет запрос ещё раз. Для сообщений это безопасно (ключ от повторов), для нажатия кнопки под
  сообщением — нет: бот получил бы второе нажатие («Подтвердить оплату» дважды).
- **Последствия:** пока нажатие ждёт ответа, библиотеке не дают переподключиться самой (соединение открывает обработчик
  Pepa, и он отказывает): запрос завершается ошибкой, итог — «неизвестно», решение — за пользователем, а подключается
  заново уже Pepa. Если связь всё же переподключалась или Telegram ответил «-503» во время нажатия, итог тоже
  «неизвестно». Кроме того: ошибка кода JavaScript после начала выполнения — «итог неизвестен» (код мог изменить
  страницу), а ошибка разбора (в том числе «return» вне функции) — «код не выполнялся»; ключ от повторов Telegram
  переносится на повтор только для того же чата; сбой связи при загрузке и сохранении файла — ошибка связи (повтор),
  а не ошибка файла; из имён файлов от собеседника убираются невидимые символы направления письма, запрещены все имена
  устройств Windows; общий путь к «Завершению» учитывается в проверке «одно окно браузера в разных ветвях»; помощник не
  повторяет запрос после ошибки шлюза (502/504). Ввод в окна Windows: окно выводится вперёд, даже если впереди его
  второстепенное окно (например, «Найти»), а поле правки, которое таблица открывает на первом символе, — тот же ввод.

## D-043. Расширения — сборки .NET со своими блоками, каждое в своём контексте загрузки
- **Почему:** пользователю нужны свои блоки и интеграции без пересборки Pepa (этап 6). Блок Pepa — это уже контракт
  `INodeExecutor` + описание, поэтому расширение — просто сборка, которая добавляет такие блоки.
- **Последствия:** контракт `Pepa.Core.Plugins.IPepaPlugin` (название и `Register`): расширение добавляет разделы палитры
  и блоки; ему доступны своя папка данных и рабочая папка. Pepa при запуске загружает каждую папку в
  `<данные>/plugins/<имя>/` в отдельный `AssemblyLoadContext`: свои зависимости расширения — из его папки, а сборки
  Pepa и .NET — общие (иначе контракты не совпали бы). Расширение принимается целиком или никак: тип блока — с точкой
  и не с префиксом встроенных блоков, без совпадений со встроенными и чужими блоками, без «Начала», «Завершения» и
  ветвления, раздел палитры существует, у блока есть выходы. Ошибка расширения (не сборка, исключение при подключении,
  неправильный блок) видна в «Настройках» → «Расширения» с причиной, а остальная Pepa работает; сценарий с блоками
  отсутствующего расширения не проходит проверку («неизвестный тип блока»). Блоки расширений подчиняются тем же
  правилам надёжности (Effect, проверка результата, «итог неизвестен») и попадают в каталог ИИ-помощника. Расширение
  работает с правами Pepa — об этом сказано в «Настройках». Пример с двумя блоками и инструкцией —
  `samples/Pepa.Plugins.Sample`.

## D-044. Выбор элемента окна в конструкторе — список из дерева UI Automation, без угадывания
- **Почему:** имя элемента и AutomationId трудно узнать без отдельных программ (Inspect.exe); ошибка в имени
  обнаруживается только при запуске. Нужен выбор из того, что действительно есть в окне.
- **Последствия:** в блоках окон Windows у поля «Элемент» есть кнопка «Выбрать в окне…»: Pepa ищет окно теми же
  правилами, что и блоки (заголовок и/или программа), и показывает элементы (до 600, глубина до 12) с отступом по
  вложенности. Окно не найдено — сказано прямо; подходит несколько окон — тоже ошибка с их списком, окно не
  угадывается. У каждого элемента видна надёжность поиска: «по ID» (AutomationId уникален в окне), «по имени» (имя
  уникально) или «ненадёжно» (ни то, ни другое — блок может найти несколько элементов и остановится). Выбор
  заполняет имя (точное совпадение), AutomationId — если он уникален или у элемента нет имени, и тип элемента, если
  Pepa его знает. В «Прочитать из окна» при уникальном ID имя не ставится: там имя часто и есть читаемый текст, и
  блок перестал бы находить элемент, когда текст изменится. Элемент без имени и ID выбрать нельзя. Если в заголовке окна или программе есть переменные `{{…}}`,
  выбор недоступен — окно станет известно только при выполнении. Работает только в Pepa.exe на Windows; проверено на
  имитации Windows, с настоящими программами — у пользователя.

## D-045. Запись в окнах Windows — перехват ввода + UI Automation, итоговый текст поля вместо нажатий
- **Почему:** этап 5 — запись действий не только в браузере. Записывать координаты и отдельные нажатия клавиш
  ненадёжно: окно сдвинется, раскладка другая, исправления опечаток превращаются в десятки шагов.
- **Последствия:** глобальные перехватчики мыши и клавиатуры (low-level hooks) только отмечают событие и сразу
  возвращают управление; элемент под мышью и в фокусе определяет UI Automation в отдельном потоке (сразу, пока окно не
  изменилось), а подсчёт похожих элементов в окне — в третьем потоке. Ввод программ (флаг injected — в том числе блоков
  Pepa) и ввод в окна самой Pepa не записываются; запись не начинается, пока мышь и клавиатура заняты процессом.
  Шаги:
  - нажатие → «Нажать в окне»: элемент по уникальному AutomationId (подпись остаётся проверкой), иначе по подписи и
    типу; если таких элементов в окне несколько — шаг с пояснением, при выполнении блок остановится (а не нажмёт первый);
    элемента нет (фон окна, нарисованная кнопка) — «Мышь: нажать в точке» с пояснением. Двойной щелчок и правая кнопка —
    способ нажатия того же блока;
  - набор текста → «Ввести в окне» с итоговым значением поля, прочитанным, когда набор в поле закончился (нажатие мышью,
    клавиша-команда, другое поле, остановка записи); нажатие в поле перед вводом не записывается отдельно. Клавиши
    редактирования, Ctrl+A/C/V/X/Z, AltGr и (в многострочном поле) Enter и Tab — часть набора. Поле пароля не читается —
    в блоке переменная `password`. Поле без подписи и кода — «Клавиатура: напечатать текст» с пояснением;
  - остальные клавиши и сочетания → «Клавиатура» (Enter, Escape, Tab, Ctrl+S, Alt+F4, буквы вне поля — для меню и
    списков; отдельное нажатие Alt). Alt+Tab, Win+…, знаки вне поля не записываются (с пояснением у следующего шага);
  - заголовок окна вида «Документ — Программа» сокращается до программы (с пояснением), поиск — ещё и по имени процесса;
  - перетаскивание, прокрутка, панель задач, рабочий стол и меню «Пуск» не записываются — пояснение у следующего шага.
  Шаги собирает общий код (`DesktopRecorder`), он проверен на имитации перехвата: записанные блоки выполняются на
  имитации Windows и повторяют действия. Сам перехват (`UiaInputMonitor`) собирается в CI, но с настоящими программами
  проверяется у пользователя.

## D-046. Итоги восьмой проверки: правка помощником, расширения, ввод в окнах
- **Правка помощником** не трогает то, о чём модель не сказала: у блоков, что уже были (тот же id и тип), остаются
  настройки выполнения (повторы, тайм-аут, точка останова) и поля, которые модель не назвала; пустое значение поля —
  очистить его (об этом сказано модели). Изменённые настройки видны в списке изменений до применения. Сценарий с
  повторяющимися id блоков помощнику не отправляется (ответ стоил бы денег, а блоки перепутались бы).
- **Расширения** не могут ничего сломать в Pepa при загрузке: любая ошибка кода расширения — отказ с причиной; описание
  блока читается один раз, и проверяется и регистрируется одна и та же копия; ошибка в собственной проверке параметров
  блока — замечание проверки. Отказ также, если расширение заменяет существующий раздел палитры или описание неполное
  (нет названия или описания, пустые или повторяющиеся id выходов и имена полей, поле-список без вариантов, SummaryField
  без такого поля). Пути к файлам расширение получает через `ResolveWorkspacePath` — те же проверки, что у блоков файлов.
  Pepa, запущенная от имени администратора (Windows), расширения не загружает: папка расширений — в данных
  пользователя, и сборка из неё получила бы права администратора. Не поддерживаются (сказано в причине или в инструкции):
  собственные нативные библиотеки расширения и сборки с именами сборок Pepa или .NET.
- **Проверка результата в примере расширения** сравнивает байты от запомненного места: «выполнено» — только если целая
  строка дописана, «не выполнено» — только если файл не изменился, остальное (часть строки, чужая запись) — «неизвестно».
- **Нажатие кнопки бота**: отказ Telegram (подождать, не принято) считается «не нажато», только если библиотека не
  отправляла нажатие повторно; иначе — «неизвестно».
- **Ввод текста в окно**: фокус может перейти внутрь поля (таблица открыла поле правки) только сразу после первого
  символа, один раз и не из окна целиком — в остальных случаях ввод останавливается.
- **JavaScript**: отметка «код начал выполняться» ставится после директив в начале кода и в той же строке — «'use strict'»
  действует, номера строк в ошибках совпадают с кодом.
- Ошибка диска при сохранении вложения Telegram — ошибка файла, а не связи (повтор её не исправит).
- Оставлено как есть (с запасом осторожности): во время нажатия кнопки бота любой ответ «-503» или новое соединение
  делают итог нажатия неизвестным — даже если они относились к другому запросу.

## D-047. Резервные копии базы и восстановление из копии
- **Почему:** в одном файле `pepa.db` — сценарии, процессы, история и настройки. Повреждённый диск, неудачное обновление
  схемы или ошибка пользователя не должны стоить всего.
- **Последствия:** Pepa копирует базу онлайн-копированием SQLite (запись во время копирования не мешает; копия — одним
  файлом, проверяется `quick_check` и появляется под своим именем только целиком):
  - раз в сутки (проверка раз в час — Pepa может работать неделями), хранятся 7;
  - по кнопке в «Настройках» → «Резервные копии», хранятся 10;
  - перед обновлением схемы базы новой версией, хранятся 3.

  Восстановление — вручную при закрытой Pepa: заменить `pepa.db` копией (инструкция — там же).
  Подменять базу работающей программы нельзя.

  Главное — после восстановления не повторить сделанное: в копии нет того, что процессы сделали после неё. Поэтому в
  каждую копию записывается отметка «это копия» (таблица `pepa_backup` со временем копии). Если Pepa запускается на
  такой базе, каждый незавершённый процесс останавливается с решением «База восстановлена из копии»: «Продолжить» —
  с предупреждением, или «Остановить». Процесс, уже ждавший решения, сохраняет свои варианты, к пояснению добавляется
  то же предупреждение. Затем отметка снимается. Рабочая папка с файлами не копируется.

## D-048. Уведомления: процесс ждёт решения
- **Почему:** процессы останавливаются на всём неожиданном и ждут пользователя, а он может быть не у компьютера — Pepa
  для того и работает сама. Без уведомления остановка заметна только в окне.
- **Последствия:**
  - окно Pepa на Windows мигает кнопкой на панели задач, пока его не откроют (если оно не перед пользователем);
  - по желанию («Настройки» → «Уведомления», выключено по умолчанию) — сообщение в «Избранное» своего аккаунта
    Telegram из «Интеграций».

  О каждой остановке сообщается один раз: новая остановка — это новое состояние решения. Несколько остановок за
  несколько секунд — одним сообщением. Процессы, ждавшие решения ещё до запуска Pepa, отдельно не сообщаются. Если
  после перезапуска процессы остановились, приходит одно сообщение, когда Telegram подключится (ждём до 5 минут).

  Уведомление — не действие сценария: оно не повторяется. Его сбой (Telegram не подключён, нет связи) — только запись
  в журнал Pepa и никак не влияет на процессы. В сообщении — название сценария, номер процесса и пояснение остановки
  (оно уходит только в ваш собственный Telegram). Есть пробное сообщение.

## D-049. Срок хранения истории
- **Почему:** каждый процесс оставляет шаги и журнал. За месяцы ежедневной работы база растёт на гигабайты, а с ней —
  каждая резервная копия.
- **Последствия:** «Настройки» → «Движок» → «Хранить историю завершённых процессов, дней» (по умолчанию 90; 0 — всегда).
  Раз в шесть часов удаляются завершённые (успешно, с ошибкой или остановленные) процессы старше срока — вместе с их
  шагами, журналом и ветвями. Никогда не удаляются:
  - незавершённые процессы;
  - завершённые, у которых ещё работает «родитель» или «ребёнок» (вызванный сценарий);
  - процессы, за которыми числится ресурс.

  События не удаляются: по ним Pepa узнаёт повторно пришедшее событие. Место в файле базы освобождается для новых
  записей; сам файл не уменьшается.

## D-050. Итоги девятой проверки: запись в окнах, секретные переменные, копии
- **Секретные переменные.** У переменной есть отметка «Секретная (пароль)». Записанные пароли (браузер и окна) — такие
  переменные, у каждого поля пароля своя (`password`, `password2`…: старый и новый пароль — разные значения). Движок
  заменяет их значения на «••••» во всём, что пишет о шаге: сообщение, ошибка, пояснение, результат, итог процесса. Так
  блокам (и расширениям) не нужно помнить, что им передали пароль. Значения короче трёх знаков не скрываются: они есть в
  любом тексте. Параметры шага и переменные хранятся настоящими — по ним процесс продолжается и проверяет результат после
  перезапуска; при показе их скрывает API (страница процесса, отчёт). Поле ввода секретной переменной при запуске — как
  поле пароля.
- **Запись в окнах Windows** не теряет и не удваивает действия:
  - Enter и Tab — всегда отдельные клавиши (в чатах Enter отправляет сообщение). Ввод и Enter склеиваются в один шаг,
    только если следующий текст поля — прежний, перевод строки и дальше. Если перевод строки уже попал в прочитанный
    текст, он убирается из ввода — его повторит сама клавиша.
  - Если поле очистилось сразу после Enter, текст берётся из последнего прочтения во время набора, и у шага пояснение:
    последний символ мог не попасть.
  - Нажатие «без мыши» — только у кнопок, пунктов меню, ссылок, флажков, переключателей и вкладок. У пунктов списков,
    файлов и строк таблиц нажатие UI Automation означает «открыть», поэтому они повторяются мышью.
  - Щелчок с Ctrl, Shift или Alt (выделить несколько, открыть в новой вкладке) не записывается, а поясняется: простой
    щелчок сделал бы другое.
  - Буквы и цифры подряд вне поля ввода (например, в окне удалённого рабочего стола) не записываются, а поясняются: это
    мог быть пароль. Одна буква (переход по списку) и сочетания клавиш записываются.
  - Двойной щелчок — по настройкам Windows (время и расстояние), только левой кнопкой, в том числе в точке окна.
    Нажатие, сдвинутое в пределах элемента, — щелчок, а не перетаскивание.
  - Всё пропущенное (окно не определилось, запоздавший ответ UI Automation) поясняется у ближайшего шага; сбой потока
    перехвата не роняет Pepa.
  - Действия привязаны к своей записи: запоздавшие действия прошлой записи не попадают в новую. Запись, которая не
    началась, не остаётся «идущей». Остановка, при которой перехват не ответил, сохраняет записанное с пояснением.
- **Пока идёт запись, мышь и клавиатура заняты ею** (ресурс `desktop:input`, держатель — сама Pepa, а не процесс).
  Процесс с блоками окон ждёт в очереди и продолжает после остановки записи; если ресурс занят процессом, запись не
  начинается. После перезапуска такой ресурс свободен. Кнопка «Начать запись» в окнах недоступна, если Pepa открыта в
  обычном браузере: его окно попало бы в запись.
- **Копии базы:** копия, сделанная прошлой версией Pepa (без таблицы отметки), восстанавливается в новую. Сбой
  ежедневной копии или очистки истории — запись в журнал Pepa, а не остановка этих служб; копии с датой из будущего
  (сбитые часы) не мешают ежедневной.
- **Уведомления** продолжают работать после одного неудачного чтения базы.
- **Расширения:** проверка результата (`SupportsVerification`) — только у блоков с внешним действием
  (`Effect = External`); иначе отказ с причиной.
- **JavaScript:** результат кода, состоящего только из строки (`'готово'`), не теряется из-за отметки начала
  выполнения.
- **Выбор элемента окна** сбрасывает поиск на «строгий» и убирает «.exe» из имени программы.
- Оставлено как есть: если помощник в правке вернул блок с тем же id, но другим типом, это показывается как изменение
  блока (а не удаление и добавление). Пользователь видит изменение до применения и может его отменить, а разделение
  на два действия только усложнило бы список изменений.

## D-051. Слежение за папками: новый файл — событие
- **Почему:** частая задача — разобрать файл, который положил человек или другая программа (скачанный отчёт, ответ
  системы, скан). Без слежения сценарий пришлось бы запускать по расписанию и искать новые файлы самому.
- **Как:** «Настройки» → «Слежение за папками» — папки внутри рабочей папки (до 20) с шаблоном имён («*.pdf; *.xlsx»),
  по желанию с вложенными папками и с изменёнными файлами. Файл становится событием `files` (вид `created` или
  `changed`, ключ — папка слежения; в данных — путь в рабочей папке, имя, расширение, размер, время изменения), когда он
  дописан: 2 секунды не менялся и открывается для чтения без права записи для других (пока файл пишут, так открыть
  нельзя). Временные файлы (скачиваются, открыты в Office) и скрытые не учитываются; символические ссылки и junction
  не проходятся.
- **Без повторов и без неожиданных запусков:**
  - что уже лежит в папке, когда слежение включили (или изменили шаблон, папку, рабочую папку), — не событие;
  - список известных файлов хранится на диске, и после перезапуска файлы, появившиеся без Pepa, тоже становятся
    событиями, но со временем «до запуска»: ожидающие процессы их получат, а сценарии по ним сами не запустятся;
  - пропала папка (например, отключён сетевой диск) — ошибка в «Настройках»; когда вернулась, её файлы не считаются
    новыми, и об этом сказано;
  - ключ от повторов — номер слежения, путь, размер и время изменения: о том же файле Pepa второй раз не сообщит, даже
    если событие передавалось повторно после сбоя.
- **Как пользоваться:** автозапуск «По событию» (источник `files`, вид `created`, новое поле «Ключ» — папка; во входные
  значения — `event.payload.path`) или блок «Дождаться файла» (папка, шаблон имени с подстановкой переменных, тайм-аут,
  «учитывать появившиеся раньше»). Блок для папки, за которой Pepa не следит, останавливает процесс с причиной, а не
  ждёт вечно.
- **Ограничения:** папки проверяются раз в 2 секунды (без системных уведомлений — одинаково на локальных и сетевых
  дисках); в папке слежения не больше 20 000 подходящих файлов (и 200 000 файлов и папок вообще, D-053). Файл, который
  удалили и вернули без изменений, второй раз не событие. Если сценарий сам пишет файлы в отслеживаемую папку, они тоже станут событиями — выбирайте для
  результатов другую папку.

## D-052. Итоги десятой проверки: секреты до конца, запись в окнах
- **Секретные значения не уходят через вызванный сценарий.** (Пересмотрено в D-055: данные остаются настоящими, секреты
  путешествуют вместе с ними и скрываются при показе.)
- **Скрывается и прежнее значение.** На странице процесса в параметрах шага скрыто каждое поле, где блок обращался к
  секретной переменной (`vars.password`), — так не видно и старого пароля, если переменную потом поменяли; изменения
  секретных переменных в итогах шагов, секретные числа (ПИН-код) — тоже «••••». Значение, которое шаг присваивает
  секретной переменной, скрыто уже в сообщениях этого шага (например, «неверный тип»). Тексты скрываются в самом конце
  записи шага — после проверки типов и пояснений проверки результата.
- **Запуск по расписанию:** значения секретных переменных не показываются («••••»); сохранить «••••» — оставить прежнее.
  Поля ввода секретных значений (запуск, автозапуск, значение по умолчанию) — как поля пароля.
- **Запись не берёт чужую переменную:** если в сценарии уже есть «password», пароль новой записи получает следующий
  номер. Старые записи, где «password» не отмечена секретной, не меняются — отметьте её в «Переменных».
- **Запись в окнах:**
  - набор вне поля ввода не записывается до конца, вместе с исправлениями (Backspace, стрелки) и символами с AltGr, —
    и его начало тоже;
  - поле пароля остаётся секретным, даже если пароль показали («глаз»);
  - поле читается после того, как программа приняла клавишу (а не до), поэтому текст сообщения, отправленного Enter,
    полный; ничего не прочитано — шаг просит вписать текст, а не записывает пустой; большой или медленный документ во
    время набора не читается, чтобы не задерживать разбор нажатий;
  - сдвинутое нажатие считается нажатием только на кнопках и пунктах; в списке, тексте, на холсте — это выделение
    (не записывается, с пояснением);
  - Ctrl, Alt, Shift и Win берутся из состояния клавиатуры в момент действия — «залипание» после Ctrl+Alt+Del или
    Win+L запись не портит;
  - пояснения убранных или склеенных шагов (сокращённый заголовок окна, пропущенные действия) переходят к замене.
- **Начало и конец записи — по одному:** мышь и клавиатура не остаются без «держателя» при одновременных запросах.
  Запись можно остановить и из «Выполнение» → «Ресурсы».
- **Уведомление**, для которого не удалось прочитать процесс, повторяется (до трёх раз через 30 секунд).

## D-053. Итоги одиннадцатой проверки: слежение за папками
- **Файл засчитывается, только когда он правда готов:** рядом нет его временного файла (`.part`, `.crdownload`,
  `.filepart`, `.!qB`, `.aria2`… — так скачивают Firefox, Chrome, торрент-клиенты), а пустой файл (часто это заготовка,
  в которую программа ещё запишет) должен пролежать без изменений в 10 раз дольше. На Linux проверка «файл открыт на
  запись» не действует (там блокировки только рекомендательные) — остаётся проверка, что файл перестал меняться.
- **Переименование — не новый файл:** файл или вложенная папка, переименованные или перенесённые внутри слежения (тот
  же размер, время изменения и создания), событий не дают; файлы, которые пропали и вернулись без изменений (папку
  скрыли и показали), — тоже (Pepa помнит их сутки). Не читающаяся вложенная папка — пояснение в «Настройках», её
  файлы считаются прежними, а не удалёнными.
- **Одна папка — одно событие:** папку внутри другой, за которой следят «и вложенные папки», добавить нельзя.
- **Файл, появившийся без Pepa, получает ожидающий процесс,** даже если у файла старое время (его перенесли): время
  события — не раньше прошлой проверки Pepa (оно сохраняется) и раньше запуска.
- **Шаблон имени:** разделитель — только «;» (запятая бывает в именах). В «Дождаться файла» значение переменной — часть
  имени, а не шаблон: «*», «?» или «;» из переменной останавливают процесс с причиной.
- **Ключ автозапуска для `files`** приводится к виду папки слежения («входящие/» → «входящие»), папка должна быть в
  слежении; ключ виден в описании автозапуска, в редакторе — подсказки из отслеживаемых папок.
- **Нельзя выключить или убрать слежение, файлов из которого ждёт процесс** — он ждал бы вечно; сначала его нужно
  остановить.
- **Ошибки не прячутся:** повреждённый список известных файлов — пояснение (слежение начато заново) и не мешает другим
  папкам; не сохраняющийся список — ошибка, пока не сохранится (сохранение повторяется каждую проверку).
- **Стоимость:** больше 200 000 файлов и папок в слежении (подходящих и нет) — ошибка; большое дерево проверяется
  реже; список известных файлов сохраняется не чаще раза в 30 секунд (и при закрытии Pepa) — после сбоя повтор
  отсекает защита от повторов. Рабочая папка читается один раз за проверку (смена посреди проверки не превращает файлы
  в новые). Выключенное слежение отмечено «выключено».

## D-054. Итоги двенадцатой проверки: слежение за папками
- **Скрытые вложенные папки** Pepa знает, но событий об их файлах нет — ни о старых, ни о новых. Когда папку покажут
  (или переименуют, чтобы стала видна), её файлы не новые. Нечитаемая вложенная папка, ставшая читаемой, — тоже: её файлы
  не новые (с пояснением).
- **Переименование распознаётся и тогда,** когда на месте старого файла сразу появился новый (резервная копия при
  сохранении: `x` → `x.bak`, новый `x`), когда файл переименовали до того, как он «отлежался» (пометка «появился без
  Pepa» переходит к новому имени), и когда в ту же проверку не удалось передать событие о другом файле.
- **После события или переименования список известных файлов сохраняется сразу** (переименованный обработанный файл
  после сбоя не стал бы «новым»); остальные изменения — не чаще раза в 30 секунд.
- **Нельзя выключить или убрать слежение, по которому включён автозапуск** (он молча перестал бы срабатывать): сначала
  выключите автозапуск. Выключенный автозапуск сохраняется и без слежения; ключ включённого — только папка с
  включённым слежением. Проверка и сохранение слежения — одно за другим; если в это мгновение процесс начал ждать файла
  из выключаемой папки, слежение возвращается как было. Отказ ничего не создаёт.
- **«Входящие» и «входящие» на Windows — одна папка:** при смене регистра букв остаётся прежнее написание (по нему
  ключи событий, ожиданий и автозапусков).
- **Пустое значение переменной в имени файла** («{{ vars.client }}*.pdf» → «*.pdf») останавливает «Дождаться файла» с
  причиной.
- Путь к папке, ставший недопустимым (ссылка), — как пропавшая папка: когда снова годится, слежение начинается с того,
  что есть. Расписание проверок — по монотонным часам; изменённые настройки проверяются сразу. Удалённые файлы помнятся
  не больше 20 000. Списки первой версии («{id}.json») читаются. Ограничение: на Linux у файлов нет времени создания
  (берётся время изменения), поэтому переименование там узнаётся по размеру и времени изменения.

## D-055. Секреты путешествуют вместе с данными
- **Почему:** двенадцатая проверка показала, что подмена значений на «••••» в данных ломает работу (вызвавший сценарий
  вписал бы «••••» в форму входа, повторы заблокировали бы учётную запись), а скрытие только по текущим значениям и
  только у одного процесса пропускает утечки: прежнее значение пароля, его копию, событие с паролем, сокращённый или
  экранированный предпросмотр.
- **Как:** у процесса есть список всех значений, которые были у него секретными (новая колонка `processes.secrets`,
  миграция 6): начальные и прежние значения секретных переменных, переданные вызвавшим процессом, полученные с
  событием. У события — секреты, которые в нём есть (`events.secrets`): от отправителя «Отправить событие» и от
  вызванного сценария в событии о завершении. Данные не меняются нигде: получатель (вызвавший сценарий, «Ждать событие»,
  автозапуск по событию) работает с настоящими значениями, а секреты события становятся его секретами. Скрывается всё
  при показе и в записях журнала — по значениям.
- **Что скрывается:** значение целиком, его запись в JSON (с экранированием `+`, `&`, кавычек и не-ASCII — так их
  показывают предпросмотры), начало длинного значения перед «…» или «...» (блоки сокращают значения в сообщениях),
  значение неверного типа для секретной переменной. Короткие значения (до 6 знаков, ПИН-код) — только отдельным словом
  и передаются дальше только целым значением: «1234» не скрывается и не считается секретом в номере заказа «A-12345».
  В параметрах шага скрыто поле, где блок обращается к секретной переменной в любой записи (`vars.x`, `vars?.x`,
  `vars["x"]`, `vars['x']`, кириллические имена). На странице «События» данные, ключ и ключ от повторов скрыты по
  секретам события.
- **Запись в окнах:** поле запоминается как поле пароля при первом нажатии в нём (а не только при наборе) — «показать
  пароль» до набора не раскрывает его; поле с подписью «Пароль», «Password», «PIN» — тоже пароль. Backspace перед
  набором вне поля («назад» в проводнике) остаётся. Повтор Alt определяется по состоянию клавиатуры в момент нажатия;
  медленное (но короткое) чтение поля не теряется, пустое не затирает прочитанное; выпадающие списки и ячейки таблиц —
  «пункты» (сдвинутое нажатие на них — нажатие).

## D-056. Итоги тринадцатой проверки: секреты — одно правило везде
- **Одно правило поиска** и для скрытия, и для передачи другому процессу: длинное значение — где угодно в строке,
  короткое (до 6 знаков) — отдельным словом, число любой длины — отдельным числом. ПИН «4821» во фразе «Ваш ПИН: 4821»
  уходит с событием как секрет; код «123456» в номере телефона «+71234567890» не скрывается.
- **Что помнит процесс:** пришедшее извне (от вызвавшего процесса, с событиями) — отдельно и не вытесняется; прежние
  значения своих секретных переменных — последние 500. Текущие значения секретных переменных не хранятся (они и так
  известны). Внутри секретного объекта или списка секретны строки, а не числа («HTTP 200» остаётся видным).
- **Сокращённый предпросмотр** скрыт, если перед «…» не меньше трёх знаков начала секрета (и не меньше его половины).
- **Скрыто и в списках:** пояснение и «чего ждёт» (ключ события из секретной переменной) — на странице процесса, в списке
  процессов и на «Главной»; ожидания процесса — тоже. Страница процесса читает процесс после шагов (новый секрет из
  шага не проскочит).
- **Быстро:** поиск без регулярных выражений на каждый секрет, секреты считаются до записи в базу (общий замок записи
  не держится долгими вычислениями).
- **Запись в окнах:** если поле перестали читать (медленное), а после прочтения нажато больше одной клавиши, текст
  считается неизвестным («впишите его»), а не взятым начало. Подпись «пароль» делает паролем только поле ввода и не
  подсказку, требования или «забыли пароль».

## D-057. Итоги четырнадцатой проверки: секреты без исключений
- **Ничего не забывается.** Ограничение «последние 500 прежних значений» убрано: забытое значение показалось бы там, где
  оно хранится настоящим (параметры прошлых шагов, копии в обычных переменных). Список растёт, только когда секретной
  переменной присваивают новое значение, — для обычных сценариев это единицы.
- **Числа внутри секретного объекта секретны** (CVV, ПИН-код в объекте карты) — как и всегда, только целым числом:
  «4821» скрыт в «ПИН 4821», но не в номере заказа «17374821». Цена — лишний раз скрытое число вроде «200» в процессе,
  где оно есть в секретном объекте; это безопаснее показанного CVV.
- **Скрытие за один проход:** совпадения всех секретов ищутся в исходном тексте, пересекающиеся объединяются, текст
  собирается один раз — время линейное и на большой странице с тысячами совпадений, а пересекающиеся секреты не
  оставляют хвостов. Граница слова учитывает экранирование JSON: в `"Ваш код:\nQw9z"` код — отдельное слово.
- **Передача секрета по тому же правилу:** секрет узнаётся в данных события и в записи JSON (`JSON.stringify` экранирует
  кавычки и обратную косую черту).
- **Сокращённый предпросмотр** короткого значения и числа скрыт, только если начинается с начала слова: «Обработано
  1482...» для ПИН «4821» остаётся.
- **«Задать переменную»** для секретной переменной: значение в параметрах шага скрыто целиком (и его короткие части).
- **Результат шага очищается до права записи** — общий замок записи не держится, пока ищутся секреты в прочитанной
  странице; под замком — только тексты (и результат, если его заменило решение под замком).
- **Списки процессов не копят память:** сценарии завершённых процессов не запоминаются по процессу — только по тексту
  сценария и не больше 64; набор секретов для списка строится, только когда есть что скрывать.
- **Запись в окнах:** паролем не считается только подсказка и «забыли пароль»; поле с требованиями в подписи («Пароль
  (не короче 8 знаков)») — пароль: лишний раз скрытое значение безопаснее показанного.

## D-058. Запросы к сайтам и API: два блока по тому, меняют ли они что-то
- **Почему:** многие сайты и сервисы проще и надёжнее вызывать напрямую по HTTP, чем через страницу в браузере
  (курс, статус заказа, создание заявки, оповещение в другую систему). Но запрос, который что-то меняет на сервере,
  нельзя повторять вслепую — как и любое внешнее действие.
- **Два блока вместо одного с выбором метода:** «Получить по адресу» (GET) только читает — при сбое повтор безопасен,
  ответ сервера 5xx/408/429 — ошибка с повтором по настройкам. «Отправить запрос» (POST, PUT, PATCH, DELETE) — внешнее
  действие: от того, меняет ли блок что-то, зависят правила восстановления движка, а они задаются типом блока.
- **Как понимается ответ «Отправить запрос»:** соединение не установлено (имя не найдено, нет подключения, защищённое
  соединение, прокси) — запрос не отправлен, это обычная ошибка с повтором. Ответ 4xx — сервер отклонил запрос (ошибка
  без повтора, текст ответа — в сообщении), 408/429 — «не сейчас» (с повтором), 307/308 — «отправьте на другой адрес»
  (не выполнен). 5xx, потерянный ответ, тайм-аут и 301/302/303 (так отвечают после выполненной отправки) — «итог
  неизвестен»: решает пользователь, проверить у сервера Pepa не может и поэтому не обещает.
- **Ключ от повтора (Idempotency-Key)** включается вручную — только для серверов, которые его поддерживают. Ключ один на
  все попытки одного и того же запроса (хранится в снимке шага) и новый, если запрос изменился. С ним потерянный ответ и
  5xx — ошибка с повтором: сервер второй раз не выполнит. Тайм-аут остаётся «итогом неизвестен» (остановку процесса
  от тайм-аута блок не отличает), повтор пользователем идёт с тем же ключом.
- **Без собственных переходов по перенаправлениям:** «Получить» проходит их сам (до 10) и не передаёт заголовки доступа
  (Authorization, Cookie, …key…, …token…) на другой сайт; «Отправить» не переходит.
- **Что сохраняется:** тело ответа (JSON — разобранным, текст — с учётом кодировки страницы) или ответ целиком: код,
  `ok`, адрес, заголовки, тело. Не текст и больше 5 МБ не сохраняется (переменные хранятся в базе). В сообщениях —
  адрес без параметров (в них бывают ключи). Секреты в заголовках скрыты в истории правилом секретных переменных (D-050).

## D-059. Итоги пятнадцатой проверки: секреты в любых записях и при любом их числе
- **Запись JSON.stringify.** Выражения записывают строку в JSON иначе, чем .NET: экранируют только кавычку, обратную
  косую черту и управляющие символы, а эмодзи, неразрывный пробел и U+2028 оставляют как есть. Эта запись — четвёртая
  форма каждого секрета (и при скрытии, и при передаче с событием).
- **Секрет в имени поля** (`({ [vars.password]: 1 })`) скрывается и передаётся с событием, как секрет в значении; два имени,
  ставшие одинаковыми после скрытия, сохраняются оба («•••• (2)»).
- **Один проход по тексту для всех секретов:** значения разложены по первым двум знакам, и в каждой позиции текста
  сравниваются только подходящие. Время зависит от длины текста, а не от числа запомненных секретов (процесс, который
  каждый час получает новый токен, со временем помнит их тысячи). Секреты публикуемого события считаются до права
  записи.
- **Числа короче 4 цифр** (CVV внутри секретного объекта) скрываются в своём процессе, но другим процессам секретом не
  передаются: там это было бы любое «100». Если вызванный сценарий получает такое значение, отметьте его переменную
  секретной.
- **На странице «События»** данные скрыты и по секретам получателя: событие, сохранённое в секретную переменную (код из
  сообщения), — секрет процесса, который его получил или был им запущен.
- **Экранирование как граница слова** — только в тексте с JSON (есть кавычки): путь `C:\nQw9z\file` не портится. Цифры
  самого `\u1234` — не число (ПИН «1234» в нём не ищется).
- **Показ не запоминает сценарии по процессу:** устаревшая запись процесса (он уже завершился) не оставит его сценарий
  в памяти — запоминается только сценарий, по которому процесс выполняется, до его завершения.

## D-060. «Спросить пользователя»: вопрос — это ожидание события, которое создаёт только интерфейс
- **Почему:** в автоматизации бывают шаги, которые должен сделать человек: ввести код с картинки, подтвердить оплату,
  выбрать из вариантов. Раньше для этого оставалось «Ждать событие» и ручная отправка события — неудобно и легко
  ошибиться ключом.
- **Как:** блок ждёт события служебного источника `pepa.question` со своим случайным ключом (подписка с назначением
  «вопрос»). Поэтому вопрос переживает закрытие приложения, у него есть тайм-аут, а после перезапуска ответ применяется
  только после «Продолжить» — как любое событие. Вопрос (текст, варианты, картинка) — параметры шага.
- **Ответ** создаёт только интерфейс (`POST /api/questions/{id}/answer`): «Отправить событие», API событий и «Ждать
  событие» источник `pepa.question` не принимают — ответ нельзя подделать или перехватить. Ответ — одно событие с ключом
  от повторов `answer:<вопрос>`: двойное нажатие или вторая вкладка не дадут второго ответа. Вариант выбирается номером
  (его текст при показе может быть скрыт как секрет), не из вариантов — отказ, если свой ответ не разрешён.
- **Секретный ответ** (включено в блоке или переменная для ответа секретная): поле ввода пароля, в переменной — как
  введён (с пробелами), а в истории, итогах и на странице «События» скрыт: он секрет события и становится секретом
  процесса. Секреты теперь ищутся и без пробелов по краям: тексты часто обрезают.
- **Где виден:** на «Главной» (все вопросы) и на странице процесса, с картинкой из рабочей папки (только PNG, JPEG,
  GIF, WebP, BMP до 20 МБ). О новом вопросе — уведомление, как об остановке (мигание окна, по желанию — Telegram): один
  раз на вопрос, о заданных до запуска — нет.

## D-061. Итоги шестнадцатой проверки: запросы HTTP
- **Ключ от повтора не превращает неизвестное в «не выполнено».** Потерянный ответ, 5xx и 409 («запрос с этим ключом
  ещё выполняется») с ключом — ошибка с повтором, только пока повторы по настройкам блока остались; последняя попытка —
  «итог неизвестен» (решаете вы, повтор безопасен), а не выход «Ошибка». 422 с ключом — «итог неизвестен»: сервер мог
  отказать из-за ключа, уже использованного с другими данными.
- **Ключ — один на все попытки шага**, даже если данные посчитались иначе (время, случайное число): новый ключ сервер
  принял бы за новый запрос. Новый заход в блок — новый ключ.
- **Не отправлено — значит ошибка, а не «неизвестно»:** нет подключения за 30 секунд; значение заголовка не латиницей
  (кириллица) — ошибка параметров до отправки.
- **Адрес с подстановками** (новый вид поля «адрес»): подставленное в путь и параметры кодируется целиком — «/», «?», «#»,
  «..» в значении не меняют адрес; пустая подстановка там — ошибка (`DELETE …/items/{{ vars.id }}` без номера не станет
  удалением всего списка). Подстановка в начале (`{{ vars.url }}`, `https://{{ vars.host }}`) — как есть.
- **Куки не общие:** клиент общий для всех процессов, поэтому свои куки он не хранит; нужна кука — заголовок Cookie.
- **Перенаправления:** на другой сайт уходят только безобидные заголовки (Accept*, User-Agent, Cache-Control) — ключ
  мог быть под любым именем; с https на http «Получить» не переходит.
- **Без ключей в истории:** сохраняемый адрес ответа — без параметров; сообщения — без параметров и имени с паролем
  (адрес с ними не принимается); секрет ищется и в закодированном для адреса виде.
- **Кодировка страницы** — из заголовка, иначе по BOM, у страниц и XML — из `<meta charset>` / `<?xml encoding?>`. Ответ,
  названный JSON, но не разбирающийся, сохраняется текстом с предупреждением. Прокси организации — с учётной записью
  Windows.

## D-062. Итоги семнадцатой проверки: ответ — только своему вопросу и только вовремя
- **Ответ сразу отдаётся своему вопросу:** под правом записи ожидание закрывается («получено»), а событие записывается
  уже назначенным этому процессу — без общего сопоставления событий. Поэтому ответ не получит ни другой процесс, ни
  автозапуск, ни «Сопоставить снова»; вручную отдать ответ чужому вопросу тоже нельзя. Автозапуск по источнику
  `pepa.question` не сохраняется.
- **Срок ответа проверяется всегда**, и у приостановленного процесса (его тайм-аут наступит после «Продолжить»):
  вопрос с вышедшим сроком не показывается, ответ на него не принимается.
- **Вариант выбирается номером внутри движка** — после проверки «уже ответили»: вторая вкладка после ответа получает
  «уже ответили», а не «нет такого варианта».
- **Секреты в ответе:** кроме секретного ответа, секретами события становятся секреты процесса, попавшие в ответ
  (вариант из секретной переменной).
- **Ответ — в тип переменной:** число («42,5») и «да/нет» разбираются, текст и «любой» — как есть; не подходящий ответ
  не принимается и вопрос остаётся открытым (раньше вопрос закрывался, а шаг падал на типе).
- **Варианты заданы, но получились пустыми** — ошибка шага, а не «любой ответ».
- **Уведомления по номеру вопроса:** новый вопрос с тем же текстом (новая капча) — снова новость, а пауза, продолжение и
  решение по другой ветви — нет; вопрос у процесса, другая ветвь которого работает или ждёт решения, — тоже новость.
- **Картинка показывается такой, какая она сейчас** — у каждого процесса должен быть свой файл (подсказка с
  `{{ process.id }}`). В интерфейсе ответ не уходит дважды по Enter; поле секретного ответа не подставляет сохранённые
  пароли браузера.

## D-063. Итоги восемнадцатой проверки: исправления исправлений
- **Ключ от повтора:** окончательная ошибка не первой попытки шага («не отправлен», «не сейчас», отказ сервера, неверные
  параметры) — «итог неизвестен»: прежняя попытка с тем же ключом могла выполниться. Блок не знает, чем кончились прежние
  попытки, поэтому решает осторожно: вы проверите и решите.
- **Адрес:** «.» и «..» в пути — ошибка (кодирование не спасает: адрес сам убирает такие части). Подстановка в имени сайта
  (не первая в адресе) не может быть пустой и содержать «/», «?», «#», «@», «\», пробел — иначе запрос ушёл бы на другой
  сайт. Адрес целиком — одной подстановкой в начале.
- **Ответ числом:** код с нулём в начале числом не принимается (стал бы другим) — для кодов переменная-текст; «NaN» и
  бесконечность — не числа. Секретный ответ скрыт и в том виде, в каком сохранится (число без пробелов).
- **Варианты должны помещаться в переменную:** если ни один вариант не превращается в её тип (переменная «да/нет», а
  варианты «Оплатить/Отменить»), шаг останавливается с понятной причиной, а не задаёт вопрос, на который нельзя ответить.
- **Уведомления:** о каждом новом вопросе (в том числе втором вопросе другой ветви) и новой остановке — каждое, даже в
  одной пачке; если вопросы не прочитались, известные не забываются, а прочитать пробуем снова.
- **Куки при перенаправлениях:** кука, поставленная сайтом по дороге (вход с перенаправлениями), уходит на следующий шаг
  перенаправления по своим правилам — только в пределах этого запроса.
